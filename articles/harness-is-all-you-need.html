The harness is all you need: an LLM that repairs 1,400 rules and decides nothing

I put a language model inside a production maintenance pipeline. The model proposes, deterministic code verifies, a human approves. Tripling the model did nothing. Narrowing what it sees doubled precision.

I Ierofantis · 9 min read · from my essay on dev.to
🔧

Four hundred thousand extraction failures landed in one run. A hundred and thirty-seven pieces of evidence reached the model. That ratio, roughly one in three thousand, is the whole design. Everything else in this post is an explanation of why the model should see so little, and why the parts of the system that never call a model are the parts that determine whether it works.

The problem shape is common. You maintain a large set of small rules, in my case around 1,400 selectors and patterns that locate a price or a title inside pages from as many external sites, covering about 1.6 million monitored items. The sites change without telling you. A rule silently returns the wrong value, or nothing. Any engineer can fix one in minutes once the evidence is in front of them. The cost is volume and triage, not difficulty.

That looks like a job for an LLM, and it is, with one catch that shapes everything: a wrong repair is silent. A wrong function throws. A wrong rule returns a value, the pipeline stays green, and the data quietly rots. So the naive design, collect failures, show them to the model, apply the answers, is not merely risky. It is a machine for producing plausible garbage with no alarm attached.

The generator has one job and no authority

The vocabulary I settled on is deliberately blunt. The generator is the model: evidence in, candidate rule out. The oracle is deterministic code that decides whether a candidate is acceptable. A gate is an oracle check that can only demote a verdict, never promote one. The adjudicator is a human, and the only writer to production. The harness is everything except the generator.

Say that list out loud and the asymmetry is obvious. Everything that decides anything is either deterministic code or a person. The model is a suggestion box.

The central claim, measured in production: the quality of a repair pipeline is governed by the oracle and by the evidence handed to the generator, not by the generator. A model three times larger produced no usable gain. Constraining the prompt and narrowing the evidence roughly doubled precision.

Stage one: refuse most of the work

The highest-value stage costs nothing and is the one teams skip. Before decoding a single page, partition failures by who can fix them, using metadata alone. Access denied belongs to the anti-abuse team. Entity deleted at the source belongs to nobody, it is gone. Gateway unreachable belongs to infrastructure. None of those are rule problems, and a model handed them will confidently propose repairs for failures no repair can touch.

In my estate, 78% of failures attributed to something other than the rule. In one run, 29,852 failures traced to a single dead gateway, a five-minute config fix. Two rules for building this stage: buckets must be mutually exclusive and exhaustive, computed by a single first-match-wins chain and asserted to sum to the total; and each bucket names a team, not a symptom. When I replaced four independent conditions with one exclusive chain, 4,307 failures that had matched nothing for months appeared in the catch-all.

Stage two: one representative per mode, plus a sibling

N failing instances collapse into K distinct failure modes, where K is the number of genuinely different repairs required. Group by structure, the vocabulary of identifiers and the template shape, never by content. Hard-split on cheap categorical facts first, cluster softly only within each partition.

Then take one representative per mode and carry a sibling: a second instance of the same mode that the generator never sees. A candidate validated on exactly one example is indistinguishable from a candidate that encodes that example. Requiring it to hold on the sibling is the cheapest generality test you will ever run.

One run compressed 26,481 failures into 114 representatives in 88 seconds. Most sources had one mode; a minority had two or three, and that minority is precisely what "one instance per source" deduplication silently mis-repairs. The same stage also threw out 424 of 561 candidate groups because the evidence was the wrong kind: listing pages instead of product pages, error notices instead of content. My loudest source by raw failure count was one of them. Thousands of failures, zero possible repairs, because 99.9% of its evidence did not contain the value at all.

Stage three: show the model less

Do not hand the model the whole page. Anchor on the strongest signal for the value you want, expand to a bounded context, attach only the metadata that could plausibly carry the answer. My focused view is about 5% of the input.

This is not a token-cost trick. The excluded 95% is where the wrong answers come from: repeated blocks, adjacent products, alternate renderings of the same value. Cutting it removes a class of error instead of trading one for another. The hazard is real too: when I finally measured instead of assuming, the correct value sat outside the focused window on about one instance in ten for one of my two fields. On those the model mostly declined, which cost recall and protected precision, and it pointed at the single highest-value fix available, widening the anchor for that field. Not touching the model.

The prompt is a contract, not a request. It frames the task as repair ("this rule stopped working, here is the evidence, what should it be"), not discovery, so the model stays anchored to the semantic slot instead of any plausible value on the page. It states prohibitions with reasons: no positional indexes, because one candidate that counted siblings returned garbage the moment an optional element appeared; no state-dependent conditions, because one keyed on a "in stock" marker worked perfectly until the state changed and then returned nothing, silently. And it states, explicitly, that declining is a correct answer.

That last clause carried most of the precision gain. Across every prompt change I made, the count of genuinely good candidates on a fixed set barely moved, eight to eleven, while precision went from 40% to 91%. Nothing I did made the model better at finding answers. Everything I did made it better at not inventing them.

Two mechanics matter here. Temperature zero, seed pinned, or you cannot tell a design change from sampling noise; before pinning, two identical runs disagreed on 4 of 46 slots, the same magnitude as the changes I was trying to evaluate. And a critique loop of exactly one round: run the cheap checks, tell the model what its candidate actually matched, allow one revision. Iterating until it passes is overfitting to a single instance with extra steps. In practice the second round mostly produces withdrawal, and withdrawal is a win.

Stage four: the oracle runs production code

Verify a candidate by executing the same parser, normalisation and coercion that production will run. Never a reimplementation, never "the model says it matches". A reimplemented oracle drifts, and its drift is indistinguishable from model failure, so you end up tuning the prompt against a bug in your own verifier. I needed a fast in-loop checker anyway, so I measured the two against each other: 3.2% of candidates were decided differently. Tolerable, and large enough that assuming zero would have been a mistake I could never have found later.

Checks run cheapest first: syntax, uniqueness (resolves to exactly one element), value (the production consumer accepts it), generality (holds on the sibling), form (no forbidden constructs). Then the two gates everyone forgets.

  • The regression gate needs something most pipelines do not keep: evidence of success. Store, per source, the most recent input the rule worked on and the value production derived. Without it, every candidate is judged only where the incumbent fails, the one place it is guaranteed to lose, and you ship repairs that fix the broken minority while breaking the working majority. This store caught thirteen candidates in its first run.
  • The null-hypothesis gate asks whether the incumbent already works on the failing evidence. If yes, the rule is not the cause, and the candidate gets demoted with a pointer to the real question.

Gates only demote. That asymmetry is what lets you add gates forever without re-validating a single past approval.

Stage five: a human, with the right screen

The adjudicator is part of the system and the display is part of the design. Show the incumbent and the candidate side by side with what each yields on the same evidence. Show the counts behind the verdict and the honest impact summed across merged modes. Show the model's self-reported confidence, de-emphasised, because it is the only unverified number on the card. Make the candidate editable before approval: a large share of near-misses need one qualifier, and an edit field turns them from rejections into repairs in seconds.

The strongest instrument is the trial: run incumbent and candidate over fifty currently-failing and fifty currently-working real instances, report per-instance. Three candidates in one batch carried the same oracle verdict. Under trial, one went from zero of fifty to fifty of fifty, a real repair. One was thirty-three of thirty-three before and after, byte-identical output, pure churn. One had no testable population at all. Same verdict, three correct decisions, three different actions.

And approvals must be durable. Before I added rejection memory, the monthly cycle re-proposed the same rejected candidates every month, reviewers noticed within two cycles, and throughput fell. A few lines of persistence recovered more reviewer time than any model change I ever made.

When precision plateaus, do not buy a bigger model

Test the instinct, because it is cheap to test. First, bucket a full run's rejections by oracle reason. Of 442 in one run, 31% resolved to nothing at all, 37% resolved to several elements, 13% broke a stated form constraint. That is 68% of failures the model's own in-loop check had already flagged, and it returned them anyway. The ceiling was compliance, not capability. And 3% were mine: a comma-decimal coercion bug that read European prices a hundred times too large. Without the categorisation I would have tuned the prompt against my own bug.

Then run the escalation experiment. Send only the rejected slots to a model three times larger, with the full context including exactly what the first candidate matched. On healthy evidence it repaired 22% and damaged 24 slots that had been working. On failing evidence it repaired none. Twelve minutes and two dollars settled an argument the team had been having for weeks. The larger model made the same two mistakes as the smaller one while looking at an explicit list of them, because the disambiguating information sat outside the evidence window. That is a retrieval problem, and you fix it by widening the evidence, not the model.

If you do escalate, do it per slot and merge back. Letting the second model rewrite whole instances moved one population from 50% to 46% through collateral damage. Restricting it to the failing slot moved the same population from 75% to 80%. The difference was never the model. It was the scope it was allowed to touch.

Report numbers that are allowed to get worse

Keep every run's raw generator output and re-score all of history with today's oracle. A stricter gate will make last month look worse and this month look worse than last month's headline. That is the metric working. Adding the regression gate dropped one precision figure from 51% to 49%; I published the drop with the explanation, because the alternative was reporting a quality gain that consisted entirely of a weaker test.

Define precision to exclude declines, and report the decline rate separately; it bounds recall, but it is not an error. And never average populations of different difficulty. My lab figure is 91% on twenty-three hand-picked instances where a repair was known to exist. My field figures are 76% on healthy evidence and 49% on already-failing evidence, where a large share has no valid answer because the product is gone. All three are true. Quoting the lab number as system performance would have been the most misleading thing I could do, and entirely defensible from the raw data.

The takeaway

Seven things decide whether a system like this is trustworthy, and none of them is the model: attribution that refuses work no repair can fix; compression to one representative per real mode with a sibling; a small, deliberately chosen evidence window; an oracle on the production code path with gates that only demote; a store of success so regression can be seen; typed verdicts and durable decisions so reviewer effort accumulates; and evaluation that re-scores history and is permitted to get worse. Build those seven and a small general-purpose model is enough. Skip them and no model is.
