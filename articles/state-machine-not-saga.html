State machine, not saga

When work spans processes, the first question during an incident is "where is this item right now?" If you cannot answer, you do not have a system, you have a haystack.

I Ierofantis · 7 min read · adapted from Refactoring Data-Intensive Applications
🗺️

Inside a monolith, a unit of work is a call stack. You can see it in a debugger, and when it fails, the stack trace tells you exactly where. Split that work across services connected by queues, and the call stack evaporates. A work item is now somewhere in a pipeline, and nothing in the architecture will tell you where unless you built something that does.

Make the state explicit

The fix is to give every work item an explicit state, and to store it. As an item moves, it transitions through named states, PENDING → EXTRACTING → TRANSFORMING → LOADING → COMPLETED, plus failure states like EXTRACT_FAILED. Each item is one mutable document carrying its current state and a history array of every transition it has made. Now "where is this item?" is a lookup, and "what is stuck?" is a query: show me everything in EXTRACTING for more than ten minutes.

The payoff, stated plainly: incidents end in a query instead of archaeology. That single property is what the whole state machine buys, and it is worth more than it costs.

Why not a saga?

The distributed-systems reflex here is the saga: model the work as a sequence of steps, each with a compensating transaction that undoes it if a later step fails. Sagas are real and sometimes necessary. But a saga is machinery, something to build, operate, and teach every engineer who joins, and you should not buy it until a problem has actually arrived that demands it.

Here is the test. A saga earns its place when steps have side effects on the outside world that must be undone. If every stage before the last is free of external side effects, and the last stage is idempotent, then there is nothing to compensate: a failed run is simply retried, and a retry of the final write lands in the same place as the first. A state machine plus retries is the complete answer, and the compensating transactions would have nothing to compensate.

When the saga arrives

The deferral has a precise trigger, and naming it is the point. The day a final stage grows a non-idempotent write, or an early stage acquires a real-world consequence that genuinely needs undo, the saga stops being deferrable and its costs must be paid. What does not trigger it is fashion, a conference talk, or the feeling that the system has grown important enough to deserve heavier patterns. A pattern is a purchase. The reason to make it is a problem that has actually happened.

The general shape

Track where work is with explicit, stored state. Keep stages side-effect-free until the last, and make the last idempotent, so retries are safe and compensation is unnecessary. Reach for the heavier coordination pattern only when a real non-idempotent side effect forces it. Most pipelines never reach that day, and the ones that do will know exactly when they did.
