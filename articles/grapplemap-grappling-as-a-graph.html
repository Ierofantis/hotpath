GrappleMap: modeling grappling as a graph of positions

What if you modeled an entire martial art as a directed graph, where every vertex is a frozen pose and every edge is a move? That is exactly what GrappleMap does, and it is one of the most elegant data models I have worked in.

I Ierofantis · 8 min read · deep dive
🥋
A quick credit before anything else: GrappleMap is an open-source project by Eelis van der Weegen. I have been hacking on its tooling, and this is a deep dive into how it works, not a claim to have built it. Links to the real thing are at the bottom.

Grappling is usually taught as a list of techniques: here is an armbar, here is a sweep, here is an escape. GrappleMap throws that framing out. It treats the sport the way you would treat a state machine, and once you see it that way you cannot unsee it.

Positions are states, moves are edges

The core model is a directed graph. Each vertex is a concrete pose of two stick-figure players, the full 3D configuration of both bodies at one instant. Each edge is a transition: a short animation carrying one position into another. A technique, in this model, is not a special object at all. It is just a path through the graph.

This is the move that makes everything else fall out for free. "How do I get from side control to a kimura?" becomes a graph query. "What can I do from here?" is the set of outgoing edges. Chaining techniques is path-finding. A whole art collapses into states and transitions between them, which is the same shape as a pipeline, a parser, or a game's animation system.

The reusable idea: when a domain feels like an endless list, look for the states hiding under the verbs. The list of techniques was always a set of edges; nobody had drawn the vertices.

Naming and tags, layered on top

Interconnection alone is not enough to navigate thousands of poses, so positions and transitions are also named and tagged. Tags do triple duty: broad domains (side_control, deep_half), fine-grained pose facts (bottom_supine, top_posture_broken), and the presence of specific grips or controls (kimura, crossface, arm_drag). The graph gives you structure; the tags give you filters across it.

How a pose is stored

The database is a single text file, and it is wonderfully blunt. Each entry is a name, a tags: line, and then blocks of compact encoded text that hold the actual geometry: the coordinates of every joint of both stick figures, packed into a dense base-something string. A position looks roughly like this:

side ctrl w/\nnear open elbow\nand crossface
tags: side_control top_underhook bottom_supine crossface
    Q2aAwQJFazuRQGddznKqcxxSRkbTzoJpbsxEToa1FVGgaYDSPnfgB7LGfaCxRle1LbLSf
    nLOSubdIJKoaVL8QsaUMqOmauNOP1azNAPva9NNPnblOlQAauNFN2ffGdOFe9MbPefdOP
    ...

That encoding is the quiet genius of the format. Poses are high-dimensional (two bodies, many joints, three axes each), but storing them as opaque compact strings keeps the database diffable, greppable, and mergeable in plain Git, which matters enormously for a community-edited dataset. Transitions are stored as keyframes between two such poses, and the tools interpolate the frames in between.

The tools around the graph

A data model is only as good as what you can do with it, and this is where the project gets deep. There is a web composer and explorer for walking the graph, an editor for posing the figures, a native editor, even a VR interface. The pipeline that renders scripted or random matches into videos is pure graph traversal turned into animation.

The corner I have spent the most time in is the diff utility (diff.cpp), which summarizes a changeset: which positions moved, which edges were added or removed, which tags changed. For a dataset that lives in Git and is edited by many hands, a semantic diff, one that speaks in positions and transitions rather than raw encoded lines, is what keeps review humane. It is the same problem every collaborative data project eventually hits: your version control diffs bytes, but your reviewers think in domain objects.

Why this shape keeps paying

GrappleMap's stated goals include being an index into the instructional literature, a source of drills, and, maybe one day, a training set for machine learning that could discover new jiu-jitsu. Every one of those is only reachable because the art was modeled as a graph first. You cannot generate drills from a list of techniques; you can generate them from paths through a graph. The data model was not a detail. It was the thing that made the ambitions possible.
