The strangler fig: rebuild a live system without a rewrite

You have a legacy system that earns money and hurts to change. The clean rewrite is the option everyone wants and the one that usually dies. There is a third door.

I Ierofantis · 8 min read · adapted from Refactoring Data-Intensive Applications
🌿

Every team holding an aging system eventually faces the same three doors: keep patching, rewrite from scratch, or rebuild incrementally while the old system keeps running. The first has no exit. The second is the one every engineer secretly wants. This is about why the third door is usually right, and why the second one kills projects.

The case against the big rewrite

Start with what the old system actually contains. Its value was never its structure, which is poor. It is the accumulated fixes and special cases written into the code over years: undocumented answers to how each external system really behaves. A rewrite discards those answers and must then rediscover every one, and the only discovery mechanism available is failing in production, in front of customers who were not consulted. For a data-intensive system, feature parity is not a checklist you can read off the old code. Most of the features are invisible until they are missing.

Then comes the valley. From the day a rewrite is announced, the old system is condemned, and nobody invests in condemned code, so it decays faster. Meanwhile the new system is not yet trusted, because trust is only earned by running against reality for a long time. The result is a long stretch where revenue depends on the system nobody maintains while the best engineers work on the system nobody believes. Many rewrites die quietly in that valley.

The reframing: treat the legacy code as an asset to be wrapped and called, not a liability to be replaced. Its value is exactly the knowledge a rewrite would throw away.

How the strangler fig works

Stand up a new system around the old one. From the first week, the new system owns the scheduling, the queues, the state tracking, and the deployments. The old code keeps doing exactly what it did yesterday: reading from the same external systems, running the same logic, writing to the same database, unaware anything changed around it. A thin bridge lets the new orchestration call the old logic, often as a subprocess speaking JSON over stdin and stdout.

Then you retire the old code piece by piece, each piece on its own schedule, each retirement reversible. One source's logic gets reimplemented behind a clean interface and cut over; if it misbehaves, you flip back. The old system shrinks one component at a time until there is nothing left but the bridge, and then you delete the bridge too.

The bridge exists to be deleted

That framing matters. The bridge between old and new is not architecture you are proud of; it is scaffolding with a lifespan. It exists so that the migration can be incremental and reversible, and its whole purpose is to be removed once the last piece of legacy behind it is gone. Building it well means building it to disappear.

When a rewrite is actually right

To be fair to the seductive door: a rewrite is correct when the legacy logic is genuinely small enough to reproduce in weeks, or so broken that wrapping it would preserve bugs rather than knowledge. Short of that, the honest comparison is not risky-migration versus safe-status-quo. It is a risk taken deliberately, on a schedule you choose, against a risk absorbed passively, on a schedule chosen by the next outage. Framed that way, the third door usually wins.
