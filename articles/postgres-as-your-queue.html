You probably don't need Redis: Postgres as your job queue

The 2026 revival of "just use Postgres" is not hype. For a job queue, pub/sub, and cache-style writes at moderate scale, the database you already run and back up does the job.

I Ierofantis · 7 min read · on a current trend
🐘

There is a reflex, the moment you need a background job queue, to add Redis or a broker. Another service to run, monitor, back up, and keep consistent with the database that holds your actual truth. For a lot of systems that reflex is premature, and the tool that removes it is one you are already running. Postgres grew the primitives for this years ago, and in 2026 people are finally leaning on them.

A queue in one clause: SKIP LOCKED

The classic problem with a SQL table as a queue is many workers grabbing the same row. FOR UPDATE SKIP LOCKED solves exactly that: each worker locks and claims a row, and any row already locked by another worker is skipped rather than waited on.

-- each worker claims one job; locked rows are skipped, not queued behind
SELECT id, payload
FROM   jobs
WHERE  status = 'queued'
ORDER  BY created_at
FOR UPDATE SKIP LOCKED
LIMIT  1;
-- then: mark it 'running', do the work, mark it 'done' (or retry).

That is a concurrent, fair-ish work queue with no extra infrastructure, transactional with the rest of your data, and visible to every tool you already use to inspect Postgres.

The real win is not performance, it is coherence. Your jobs live in the same database as your data, in the same transaction, with the same backups and the same query tools. You deleted a moving part, and moving parts are where incidents live.

Pub/sub and cache, same story

Two more Redis reflexes have Postgres answers:

  • Pub/sub: LISTEN / NOTIFY gives you lightweight event notification between connections, enough to wake workers the instant a job is enqueued instead of polling on a timer.
  • Cache-style writes: an UNLOGGED table skips the write-ahead log, trading crash-durability for speed, which is exactly the trade a cache wants.

Between these three, a large fraction of "we need Redis" turns into "we need one more table and one more clause."

When to graduate

This is not a claim that Postgres beats a dedicated broker at the top end. It does not. Once your queue throughput starts competing with your database's real workload for connections and I/O, or you need fan-out, partitioned consumers, and multi-day retention, a purpose-built system earns its keep. The honest rule is the same one this blog keeps landing on: do not buy the heavier tool until a measured problem demands it. At moderate scale, the measured problem has not arrived, and the extra service is pure cost.

The takeaway

Before you add a broker for a queue, a cache, or a notification bus, check whether the database you already operate can do it with SKIP LOCKED, LISTEN/NOTIFY, and an UNLOGGED table. Often it can, and every service you do not add is a service you never have to operate at three in the morning.
