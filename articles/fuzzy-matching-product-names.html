Fuzzy matching product names: Levenshtein, token scorers, and why you layer them

You scraped a product page and there is no barcode, no shared id, nothing but a URL slug. Now match it to the right row in a catalog of a million product names. This is how, and why one scorer is never enough.

I Ierofantis · 9 min read · from my scraping stack
🧩

Half of real-world scraping is not fetching the page. It is joining what you fetched to what you already have. When a page carries an EAN or a shared identifier, the join is exact and boring. When it does not, you are left holding a URL slug like samsung-galaxy-s21-128gb-gray and a catalog of product names, and you have to decide which name that slug means. The names are written a dozen ways: words reordered, sizes and colours appended, the brand moved to the front. Exact string equality is useless here. You need to score by meaning, not by literal spelling.

The honest floor: edit distance

Levenshtein distance is the number of single-character edits, insert, delete, or substitute, needed to turn one string into another. Turning galaxie into galaxy costs two: substitute the i for a y, delete the trailing e. It is pure mechanics, no notion of words, and it is the honest foundation everything else sits on, because it counts real changes.

You compute it as a dynamic-programming matrix. Each cell is the cost to align the two prefixes up to that point, filled from three already-solved neighbors, and the bottom-right cell is the answer.

cost = min(
    above + 1,                    # delete
    left  + 1,                    # insert
    diag  + (0 if a == b else 1)  # substitute
)

    ""  g  a  l  a  x  y
"" | 0  1  2  3  4  5  6
 g | 1  0  1  2  3  4  5
 a | 2  1  0  1  2  3  4
 l | 3  2  1  0  1  2  3
 a | 4  3  2  1  0  1  2
 x | 5  4  3  2  1  0  1
 i | 6  5  4  3  2  1  1
 e | 7  6  5  4  3  2  2   <- galaxie vs galaxy = 2

The shared galax rides the diagonal at zero cost; only the i to y substitution and the deleted e cost anything. Why the matrix and not the obvious recursion? Because trying every alignment branches three ways per character, which is exponential and re-solves the same sub-comparisons millions of times. The matrix is O(n times m), each cell filled once in constant time. Brute force is correct but slow, greedy is fast but wrong, and dynamic programming is the only approach that is both.

From distance to a score

Distance is an integer that grows with string length, so you scale it to a similarity percent: ratio = (1 - dist / (len_a + len_b)) * 100. A hundred is identical, zero is nothing shared. This raw ratio is where most people stop, and it is where most people get bad matches, because it compares the whole string in order.

cat = "galaxy"             url = "galaxie"                 (a typo, distance 2)
  ratio 85    token_set 85    partial_token_set 85     -> all three agree

cat = "samsung galaxy s21"  url = "galaxy s21 samsung 128gb gray"
  ratio 55    token_set 78    partial_token_set 100    -> only tokens survive

One word with a typo, and every method agrees: edit distance carries it. Reorder the words and staple on 128gb gray, and the raw ratio collapses to a number that would reject a correct match, even though a human reads them as the same product instantly.

The scorer ladder

The fix is a ladder of scorers, each removing a kind of noise the previous one still trips over:

  • ratio: raw edit distance on the whole string, order-sensitive. The floor.
  • token_set: split each name into a set of words, drop order and duplicates, compare the shared vocabulary. Now samsung galaxy equals galaxy samsung.
  • partial_token_set: the same word-set idea, but scored on the best-overlapping window, so trailing variant junk like 128gb or dual-sim stops dragging the score down.
The mental model: edit distance counts the real changes. The token scorers sit on top and decide which changes you agree to ignore. The most forgiving scorer catches the most, so it also lies the most, which is why you fence it.

Scoring a million rows is the wrong instinct

Here is the part the algorithm talk skips: you cannot run a scorer against every catalog row for every scraped URL. That is a million comparisons per page. The scorer is the last step, not the first. The real pipeline narrows hard before it ever scores:

def normalize(text):
    s = unidecode(text).lower()
    return re.sub(r"[^a-z0-9]+", " ", s)

# narrow: rarest tokens first, cap the candidate set
cands = candidate_idxs(url_tokens)[:200]
cands = [i for i in cands
         if shared(url, prod[i]) >= MIN_SHARED
         and (not REQ_BRAND or brand[i] & url_tokens)]

# score only the survivors
_, score, idx = process.extractOne(
    url_norm, [NORMS[i] for i in cands],
    scorer=fuzz.token_set_ratio,
    score_cutoff=MIN_SCORE)   # 85+
  • Normalize with unidecode plus lowercase plus tokenize, so ü and u stop being different characters and punctuation stops mattering.
  • Invert the catalog: a token points to the product ids that contain it, and common tokens get pruned so the and pro do not drag in the whole catalog.
  • Narrow using the rarest tokens first and cap the candidate list, here at two hundred, because the rare tokens are the ones that actually identify a product.
  • Score only those survivors against the cutoff.
  • Guard with a minimum count of shared tokens, and optionally require the brand to appear in the URL, so the forgiving scorer cannot hand you a confident wrong answer.

Fast, and tuned per site

The engine matters at this scale. rapidfuzz is the same Levenshtein math in C++, ten to a hundred times faster than the older fuzzywuzzy, and MIT-licensed rather than GPL, which is what makes scoring against million-row catalogs and hundreds of thousands of URLs an hour on a few cores actually feasible. And no single scorer or threshold is right for every source: one site's catalog names are longer than its slugs, so token_set wins; another's slugs are full of variant noise, so partial_token_set plus a shared-token guard wins. So the scorer and the thresholds live in per-site config, not in the code.

The takeaway

Match by meaning, not spelling. Keep edit distance as the honest floor, layer token scorers to forgive the noise you choose to forgive, and fence the most forgiving one with shared-token and brand guards. Above all, narrow your candidates with an inverted index before you score, because the elegant part of this problem is the scorer and the part that makes it ship is never running it a million times.
