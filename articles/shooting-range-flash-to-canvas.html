Shooting Range: resurrecting a 2016 Flash game with zero assets

The first game I ever shipped was a .swf. Nothing can open it anymore. So I rebuilt it as one canvas and one script, where every sound and every sprite is generated at runtime, and the whole thing deploys with no build step.

I Ierofantis · 6 min read · side project
🎯

There is a file in one of my oldest repos called shooting.swf. In February 2016 it was a game: two targets jumping around a stage, a pistol cursor, a 60-second timer, a gunshot sample. Today it is a fossil. No browser will run it, and the ActionScript 3 source next to it is a hundred lines that reference symbols living inside a binary .fla I cannot even open. If you started in the Flash era, you have a folder like this too.

I did not want to emulate it. I wanted to reissue it: same idea, same 60 seconds, built so it cannot rot again.

What the original actually was

Reading the AS3 was humbling. A Timer fires every 500 ms, decrements the clock, and teleports two MovieClip targets to random spots inside a 200 by 200 rectangle. Click the good one, your score goes up. Click the bad one, the CPU scores instead. That is the whole game. Everything that made it feel like a game, the gun sprite, the target art, the shot sound, lived in the .fla library as embedded assets.

That is exactly why it died. The logic was trivial and portable; the assets were locked in a proprietary container behind a runtime nobody ships. The lesson is not "Flash bad". It is that the code was never the fragile part.

The rule I built the remake around: a game that depends on nothing cannot be killed by anything. No sprites, no samples, no bundler, no framework. If the browser can draw a circle and make a tone, that is the whole dependency list.

One canvas, one script

The remake is index.html and game.js, and that is the entire deploy. The HTML is a 960 by 540 canvas with cursor: none so the crosshair can be drawn in-game. The script is a single IIFE with a fixed-step loop: update targets, resolve input, draw. No dependencies, no build.

Targets are concentric circles drawn each frame. The pistol is a few rotated rectangles that kick back on fire. Muzzle flash is a bright polygon that lives for two frames. Screen shake is a random offset applied to the whole context before drawing, decaying every tick. None of it is art in the asset sense; all of it is a handful of numbers.

Sound with no sound files

The original shipped a gunshot sample. The remake ships none. Every sound is synthesized on the fly with the Web Audio API:

  • A gunshot is a short burst of white noise through a fast-decaying gain, plus a low triangle oscillator that ramps from a thump frequency down to 40 Hz. Change two numbers and the pistol becomes a shotgun.
  • A hit is a small chord of sine tones whose pitch rises with your combo multiplier, so a streak literally sounds higher.
  • A decoy hit is a rude 110 Hz square wave. You will not need the red flash to know you messed up.

Each weapon carries its own sound: { freq, dur, thump } block next to its fire rate and magazine size. The audio is data on the weapon, not a file on disk, so adding a fifth gun is one object literal.

Three target colours, one design idea

The 2016 game had a good target and a bad target. The remake keeps that and sharpens it. Red targets score by ring: bullseye 100, inner 50, outer 25. Black decoys cost 100 and reset your combo. Gold targets are smaller and die faster, but pay 150 and add two seconds to the clock.

That last one is the mechanic I care about. In a 60-second game the only currency that matters is time, and gold is the only way to buy it. So the fast player does not chase the biggest red; the fast player chases gold, and the decoys are there to punish exactly that greed. Combos step the multiplier up to 5x, one step every five hits, and a single miss or decoy drops you to 1x. Same cruelty as my other games: the punishment changes the run, not just the score.

Four weapons from one table

Weapons are rows in an array. Pistol is the baseline. Shotgun fires seven pellets in a spread and is the only sane way to clear a cluster. SMG is full auto with a wobble. Sniper is slow and doubles points, and it pierces: the hit test walks every target under the cursor instead of breaking after the first, so stacked targets fall together. That whole difference is one if (!w.pierce) break; inside the loop. The rest of the feel, kick, shake, barrel length, is numbers on the row.

Deploying a game that has no build

The repo still holds the .fla and .swf as history, and I did not want three megabytes of dead Flash served next to the live game. So the playable files sit in public/, and a five-line Render blueprint points at that folder:

services:
  - type: web
    name: shooting-range
    runtime: static
    buildCommand: echo "static site, nothing to build"
    staticPublishPath: ./public

Push to master, Render serves the folder. No Node, no bundler, no container. It is the same pattern this blog runs on, and for a 22 KB game it is the right amount of infrastructure, which is almost none.

The takeaway

When you look at an old project and decide whether to save it, do not ask whether the code still runs. Ask what it depends on, and whether each of those things will still exist in ten years. The original had four dependencies: a runtime, an authoring tool, a container format, and a sound file. The remake has one, the browser. That is the difference between a game and a fossil.
