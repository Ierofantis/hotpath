The cookie handoff: let a browser solve it, then let curl fly

An HTTP client cannot run JavaScript, yet a warmup beats defenses that demand it. The contradiction dissolves once you split the work between two processes.

I Ierofantis · 7 min read · adapted from The Quiet Fetch
🍪

Here is a contradiction I had to resolve to scrape anything hard. A defense like Cloudflare returns a challenge that expects a real browser to run a script. A plain HTTP client runs no script, so it cannot solve the challenge. And yet the standard technique for beating these defenses at scale is a warmup, which somehow lets a fast client through. Both facts are true. The resolution is that the work is split between two processes along one clean line.

Two phases, two tools

Phase one is a real browser. It loads the target's entry page, the challenge script runs inside that browser, the runtime is probed, and on a satisfactory answer the defense sets a token in the cookie jar. This is slow and memory-hungry, but it happens once per token, not once per request.

Phase two is a fast HTTP client. You export the cookies from the browser and attach them to the client's requests. The client runs no script and solves nothing. It is simply the bearer of a valid token, and a defense that sees a valid token serves the content without re-challenging.

Phase 1  (browser, once)   load entry page → script runs → token set
                           export the cookie jar
Phase 2  (client, N times) attach token → fetch fast → spend the trust
on rejection               back to Phase 1 → refresh → resume
The mental model: the browser is the solver (runs JS, slow, expensive). The client is the replay agent (no JS, fast, cheap). A cookie is the bridge, because a token, unlike a rendered-canvas hash, is just bytes on the wire.

The three conditions

The handoff only works if the client respects the binding the defense put on the token. Get any of these wrong and it fails silently:

  1. Same address. The token is bound to the IP that solved the challenge. Present it from a different exit and it is rejected.
  2. Coherent identity. The client's TLS fingerprint and headers must match the browser that earned the token. A Chrome-solved token spent by a client impersonating Firefox is two identities that cannot both be true.
  3. Validity window. The token lasts a bounded time and request count. The client's burst has to finish before it expires.

This is why the earlier idea of "just move the cookie to curl" disappoints so often. The cookie can be reused, but only by a presenter that reproduces the whole binding.

The refresh loop

Because the token expires, the pattern is a loop, not a one-shot. The client fetches until a response tells it the token died (a challenge shell, or an empty body where content should be). Then the work goes back to the browser, the page reloads, a fresh token is minted, the cookies are re-exported, and the client resumes. Tune the loop by matching the client's burst length to the token's budget: long enough to amortize the browser's cost, short enough to finish before expiry.

Where it stops working

Against the strictest defenses, the token's life shrinks toward a single request, or the defense demands fresh runtime evidence on essentially every request. Then the loop saves nothing, because there is no burst to amortize the expensive solve across, and the honest move is to run every request inside the browser that already holds the trust. The handoff is for the common case where a token lives far longer than one request. Naming that boundary, per target, before you build against it, is most of the skill.
