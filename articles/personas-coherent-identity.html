Personas: give your scraper a coherent identity

A Chrome User-Agent over a Firefox TLS handshake is not a clever hybrid. It is an identity that cannot exist, and impossible identities are the easiest thing in the world for a defense to catch.

I Ierofantis · 7 min read · adapted from The Quiet Fetch
🎭

A modern defense does not score one signal. It scores the coherence of many: the TLS handshake, the protocol tuning, the User-Agent, the header set, the client hints. Each must describe the same browser. Set a Chrome User-Agent while your handshake is a Python library's, and you have not disguised yourself, you have presented two witnesses who cannot both be telling the truth. That contradiction is a stronger signal of automation than an honest, non-browser fingerprint would have been.

Make identity an object

If coherence across every layer is what keeps you alive, then coherence should not be a discipline you remember to apply on each request. It should be an object that cannot be constructed incoherently. Call it a persona: one record that carries a User-Agent, a full matching header set, the browser family, and the TLS impersonation target, all descending from a single choice of which browser this identity is.

The construction order is what guarantees it. Generate the header set for a chosen family. Read the User-Agent out of that set, so it agrees by construction. Detect the family from the User-Agent, and look up the TLS target from the family. Every field descends from one generation step, so there is no point at which a Chrome header set could be paired with a Firefox handshake. The impossible identity is not rejected by a check; it is simply unreachable.

Bind, do not check. Per-request validation is a call someone must remember in every code path, forever, including the ones added next year by someone who never read this. One missed path leaks a silent contradiction. Binding removes the whole class of failure by making the wrong thing impossible to express.

A pool with a metabolism

One identity used at any volume gets noticed, so you keep many, and more than quantity you need a discipline for how each is used over time. A pool of personas has three lifecycle events:

  • Cooldown. After use, a persona rests for a randomized interval before it can be handed out again, so no single identity accumulates a volume that looks automated.
  • Burn. When a persona is challenged or blocked, it is not rested but retired, and a fresh one is generated to replace it. Resting a marked identity only sends it back to be recognized again.
  • Session exhaustion. Even an uncompromised persona steps aside after a randomized budget of requests, because real browsing happens in bounded visits, not endless streams.

Together these produce a population that behaves, in aggregate, like a crowd of real users: each active in short bursts, each resting between them, each visit of bounded length, and anything that draws suspicion removed rather than nursed.

The takeaway

Stop thinking in headers and start thinking in identities. Bind every layer to one browser choice so incoherence cannot be expressed, then give those identities a lifecycle so no one of them overstays the pattern of a real person. Coherence is too fragile to leave to discipline, and too important to get wrong.
