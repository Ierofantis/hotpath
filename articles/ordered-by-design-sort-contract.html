Declare your sort order and delete half your memory

One sentence changes how a system combines data: when producers declare sort order as a first-class contract, consumers can select optimal algorithms without guessing. The state they keep collapses.

I Ierofantis · 8 min read · from Ordered by Design & my streaming SQL work
↕️

Most data systems treat sort order as something that happens at runtime, if the optimizer decides it is worth it. I have come to think that is backwards, and a whole paradigm falls out of turning it around. The thesis fits in one sentence: when data producers declare sort order as a first-class contract, consumers can select optimal algorithms without guessing.

Two ways to combine data

Consider joining data from two independent sources.

Without a contract, the consumer receives rows in undefined order. To match keys it must build an auxiliary structure, a hash table, and materialize state proportional to the dataset. It is compensating, with memory, for a guarantee it was never given.

With a contract, the producer declares its output sorted. The consumer advances through both sources in lockstep, comparing the fronts, and never revisits what has already passed. For the common case where each key appears once per side, the auxiliary memory drops from proportional-to-data to effectively constant. The same rows are examined either way; what collapses is the state you have to hold.

left:  1  4  7  9        merge: walk both fronts in lockstep,
right: 2  4  6  9               emit on equal, advance the smaller,
match:    4     9               never look back → O(1) state
The shift is about location. Sort order stops being a runtime decision an optimizer makes fresh for every query, invisible and re-estimated, and becomes a design-time contract the producer declares once: external, visible, and stable across every use.

Why the contract is worth more than the sort

The value is not that the data is sorted. It is that the order is declared, so the consumer can rely on it without inspecting statistics or guessing. An optimizer that decides to sort at runtime pays the cost and keeps the knowledge to itself. A producer that publishes its order as a contract lets every downstream consumer, now and later, choose the cheap algorithm with confidence. The knowledge moves from inside one query plan to the boundary between components, where it can be reused.

It composes

The real power shows up in chains. If an operator consumes sorted input and declares its output sorted too, order is preserved end to end, and a whole pipeline of merges runs in bounded state instead of materializing at each step. This is not a niche trick. The same idea underlies how a columnar engine, a distributed batch system, and a streaming SQL engine all get fast: sorted in, sorted out, merge in the middle.

The streaming payoff

Streaming is where the contract stops being an optimization and becomes a necessity. On an unbounded stream you cannot materialize everything, because there is no everything; the data never ends. A declared order is what makes a join over infinite input possible in bounded memory at all: the engine knows it will never see a key earlier than the ones it has, so it can emit results and release state as it advances, rather than waiting for a completion that never comes. The contract that merely saved memory in batch is what makes the computation exist in streaming.

The takeaway

Treat order as a property you promise at a boundary, not a luxury you hope an optimizer grants inside a query. Declare it where data is produced, preserve it as it flows, and the cheap algorithms, constant-state joins, single-pass merges, streaming that releases memory as it goes, become available everywhere downstream. You are not making the sort faster. You are making the guarantee reusable.
