Notebook, August: 23 mechanisms from 223 commits

A month of git history reduced to its technical content. Each entry states the symptom, the mechanism at the kernel, protocol, query or code level, the exact fix, what verified it, and the generalisation with its limits. Nothing about what the systems are for; only what broke and why.

I Ierofantis · 26 min read · monthly notebook, from git history
📓

Method. Window: the 31 days ending 2026-08-29. Sources: ten repositories, eight with activity, 223 commits authored by me, plus a small number of teammates' commits in one repository where I reviewed the change and reproduced the mechanism. Selection: a script flags commits whose message contains a lesson marker (fix, revert, instead, was blocking, back to, root cause) and commits in each repository's hottest areas by churn, and prints their changed lines; the entries below are the mechanisms those diffs contain, grouped by technical domain rather than by repository. Redaction: counterparties, vendors, hosts, identifiers, colleagues and the purpose of every system are removed before the diffs reach the draft; numbers are kept only where they are the mechanism (thresholds, sizes, units) and dropped where they describe scale.

A. Networking inside containers

1. A lower-priority ip rule makes a later exception dead code

Symptom. Tunnel pods report Connected, but a gateway in the same cluster cannot open a TCP connection to them. Health checks on the proxied ports time out; traffic originating inside the pod works.

Mechanism. The tunnel client installs fwmark policy routing: an ip rule at priority 9 of the form not from all fwmark 0xca6c lookup 51820, i.e. everything without the mark goes through the tunnel's table. The base image's exception for the cluster CIDR sits at priority 10 and is therefore never consulted. A SYN arrives on eth0 from a cluster address; the SYN-ACK is routed by the priority-9 rule into the tunnel interface and never returns to the requester. From the gateway's side this is indistinguishable from a firewall DROP, which is where the first three hypotheses went.

Fix. Source-based policy routing for the pod's own address into a dedicated table, capturing the original gateway before the tunnel rewrites the default route:

ETH0_IP=$(ip -4 addr show eth0 | awk '/inet /{sub("/.*","",$2); print $2}')
ETH0_GW=$(ip route | awk '/default via/{print $3; exit}')
# ... connect the tunnel ...
while ip rule del from "$ETH0_IP" table 100 2>/dev/null; do :; done
ip rule add from "$ETH0_IP" table 100
ip route replace default via "$ETH0_GW" dev eth0 table 100

The address extraction uses awk: the image is busybox-based and grep -P exits non-zero there, which would have left the variable empty and the rule matching nothing.

Verification. Applied alone, without touching iptables, in the live pod; all gateway replicas reached the pod on the next probe. The same fix, independently, on a second client that used a plain default-route takeover rather than fwmark rules.

Generalisation. Whenever a process takes over the default route, replies to connections that arrived on another interface need a source-based rule into a table whose default is that interface's original gateway. Does not apply if the tunnel client itself exempts the interface's subnet at a higher priority than its own catch-all.

2. A container restart is not a fresh network namespace

Symptom. A pod with several hundred container restarts fails gateway health checks while its tunnel is healthy. Latency to the proxied port grows with restart count.

Mechanism. With restartPolicy: Always, a container restart reuses the pod sandbox and therefore its network namespace. The start script ran iptables -I INPUT -p tcp --dport 8118 -j ACCEPT and ip rule add from $IP table 100 || true unconditionally. Neither command has a uniqueness constraint: the pod carried over 1200 duplicate INPUT rules and around a hundred duplicate ip rule entries (each add is assigned a fresh priority). xtables evaluates a chain linearly per packet, so every packet paid for the whole pile, enough to exceed the probe timeout.

Fix. Delete-until-absent before every insert; -D removes one matching rule per call and fails when none remain:

while iptables -D INPUT -p tcp --dport 8118 -j ACCEPT 2>/dev/null; do :; done
iptables -I INPUT -p tcp --dport 8118 -j ACCEPT
while ip rule del from "$ETH0_IP" table 100 2>/dev/null; do :; done
ip rule add from "$ETH0_IP" table 100

Verification. Rule count read on the live pod before and after; in an unprivileged test namespace, five repeated runs produced five duplicates under the old script and exactly one under the new.

Generalisation. Every mutation of shared namespace state at container start (iptables, ip rule, routes, resolv.conf) must be idempotent, because the namespace, the emptyDir volumes and the sandbox's /etc/resolv.conf all outlive the container. Startup scripts written as if they run once are wrong by construction under Kubernetes.

3. An application that resolves its own DNS bypasses the allow-list you tested

Symptom. curl inside the pod resolves and fetches fine; the same URL through the pod's local proxy daemon returns 502 "Host Not Found".

Mechanism. Two separate resolver paths. The daemon's config hardcoded nserver 1.1.1.1, so it sent UDP 53 to a public resolver directly. The tunnel client's firewall rules REJECT outbound port 53 except to loopback, and keep doing so even with its fail-closed mode switched off. libc's getaddrinfo read /etc/resolv.conf, which the client had pointed at its own resolver on loopback, an allowed path. Same host, two resolvers, one blocked.

Fix. Rewrite the daemon's resolver at runtime from whatever the client wrote into resolv.conf, which changes per connection:

TUNNEL_DNS="$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)"
sed -i "s/^nserver .*/nserver ${TUNNEL_DNS}/" /etc/proxy/proxy.cfg

A related failure in another client: wg-quick runs resolvconf -d wg0 on shutdown, emptying /etc/resolv.conf; kubelet writes that file only at sandbox creation, so the restarted container has no nameserver at all. The pre-up hook then injected the cluster DNS ClusterIP, unreachable by design under dnsPolicy: None plus a NetworkPolicy denying in-cluster DNS egress, and the pod crash-looped on token fetch. The fallback now writes the pod's own dnsConfig resolvers instead.

Verification. Full reproduction in local Docker outside the cluster; then the sidecar's /health and /ip endpoints passing by hostname through the proxy. For the resolv.conf case, writing the resolvers into the crash-looping pod brought it up on the next restart.

Generalisation. Testing name resolution with the system resolver proves nothing about a daemon with its own nserver setting. Enumerate every resolver path a pod contains before trusting a DNS allow-list.

4. A CLI exit code means "accepted", never "reached"

Symptom. Every test pod permanently Disconnected although each start-up command returned 0.

Mechanism. The client's connect is a documented no-op unless background mode is enabled. background enable raced the daemon right after login and failed once, non-fatally; every subsequent connect exited 0 while status stayed Disconnected. A second client's fail-closed toggle behaved the same way: set returned success, but toggling it after connecting forced a reconfigure that never recovered.

Fix. Retry the enable up to 5 times with a 2 s sleep and fail hard if it never succeeds; follow every connect with a 15 × 1 s poll of status | grep -q Connected, ignoring the exit code; change daemon settings only in the Disconnected state and confirm with the matching get, not the set's return value.

Verification. Live pods on the day; the follow-up rollout commits enabled replicas that had been parked at zero after the failed test.

Generalisation. Poll the observable state you actually need; treat command exit codes as acknowledgement of the request. Especially true for daemons controlled through a CLI that talks to them asynchronously.

B. Control loops and orchestration

5. A single-shot probe cannot tell a slow scheduler from a dead target

Symptom. Pods with live connections flip HEALTHY/UNHEALTHY within one 30 s cycle; gateways OOM-restart while a client-triggered rotation of a dead pod takes ~500 s and each new request triggers another.

Mechanism. The health checker, the proxy server and the control API share one asyncio loop. Under load, scheduling jitter delays a check coroutine past its timeout for a perfectly healthy pod; a single failure flipped state. Kubernetes probes had no timeoutSeconds (default 1 s) and failed for the same reason. The rotation endpoint was expensive, awaited a tunnel reconnect, and was callable concurrently: a dozen callers in one second starved the loop.

Fix. Three independent mechanisms. Hysteresis: health_check_failure_threshold = 2 consecutive failures to flip, any success resets, transitions logged rather than samples, UNKNOWN stays UNKNOWN on one failure. Probe budget: timeoutSeconds: 5. Breaker plus single-flight on rotation:

cooldown = min(base * 2 ** (failures - 1), cap)      # 5 s -> 300 s
if pod in in_flight or now < cooldown_until[pod]:
    return None                                        # refuse; no await between check and add
in_flight.add(pod)
# on failure: drop the session and re-pick with exclude={pod}; serve the failed pod
# rather than returning 503; at most one rotation attempt per request

Verification. Unit tests: one failure does not flip a healthy pod, success resets the counter, cooldown opens and backs off exponentially, single-flight refuses a concurrent caller, re-pick excludes the failed pod. Gauges for pod health, consecutive failures and a transitions counter exported to Prometheus, with stale series removed on pod disappearance (gauges do not expire on their own).

Generalisation. Anything expensive and client-triggerable needs a breaker and single-flight or it becomes a self-inflicted denial of service; any probe sharing an event loop with real work needs hysteresis. Neither replaces fixing the loop's contention; both keep it from cascading.

6. External and internal recovery on the same cadence race each other

Symptom. A container is killed by the liveness probe at the exact moment its own reconnect loop starts, repeatedly. Separately, every restart re-authenticates against an external API, and a cleanup hook logs out on kills that were never real terminations.

Mechanism. The start script self-heals after 3 failed checks at a 30 s period (90 s). The livenessProbe was configured with the identical periodSeconds: 30, failureThreshold: 3, so kubelet and the script reached their thresholds simultaneously; kubelet won. For the auth churn: a preStop hook fires on a liveness-triggered container kill inside a still-alive pod, so "log out on exit" ran on every restart and turned restart storms into auth storms against a rate-limited endpoint. A first version of that logout, installed with trap cleanup EXIT and trap 'exit 0' TERM (needed because PID 1 gets no default signal actions), was reverted for exactly this reason.

Fix. failureThreshold: 8 (240 s) on the client that has an internal loop, unchanged on the one that does not. Login state kept in a pod-scoped emptyDir mounted at the client's state directory, seeded from a .default copy baked into the image when empty (a plain mount would shadow reference data the client needs). Login gated on a local status query. Logout only when the pod is genuinely going away:

pod_is_being_deleted() {
  [ -n "$(kubectl get pod "$POD_NAME" -o jsonpath='{.metadata.deletionTimestamp}')" ]
}

Verification. deletionTimestamp semantics checked on a throwaway cluster: set on delete, eviction and Recreate rollouts, empty on a liveness kill. Pod events traced for the race.

Generalisation. Give the cheaper recovery a full cycle before the expensive one may fire. emptyDir is pod-scoped and survives container restarts; deletionTimestamp is the only in-hook signal that distinguishes a restart from a termination.

7. Ownership and placement: SSA, spread constraints, a ConfigMap mutex, least-loaded allocation

Symptom. Four unrelated deploy failures: helm upgrade refusing with "Apply failed with 1 conflict: conflict with 'kubectl' ... .spec.replicas"; seven new replicas landing on one node and six hanging; two CI runs from one push where the second was cancelled at 0 s instead of queued; and one credential holding nine leases against a cap of eight while another had never been used.

Mechanism. Helm 4 applies with Server-Side Apply; a manual kubectl scale makes kubectl the field manager of .spec.replicas, and the declarative owner is refused until the field matches again. The default scheduler scores by free resources, so deleting pods on the crowded node frees resources there and puts replacements straight back. The CI server's concurrency: group with cancel-in-progress: false cancels instead of queuing in that version. Leases were acquired first-fit in secret order, so the first key always filled.

Fix. Never scale by hand under SSA; change values and let CI apply. Pod-count spreading:

topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway   # soft: a cordoned node never strands pods Pending
    labelSelector: { matchLabels: { component: tunnel-proxy } }

A distributed mutex built on the API server's create-if-absent, scoped to the Helm step only, TTL 1800 s with stale takeover, maximum wait 1500 s (under Helm's 30 min timeout), released in an if: always() step:

until kubectl create configmap "$LOCK" --from-literal=holder="$RUN" \
        --from-literal=acquired="$(date -u +%s)"; do
  AGE=$(( $(date -u +%s) - $(kubectl get cm "$LOCK" -o jsonpath='{.data.acquired}') ))
  [ "$AGE" -gt "$LOCK_TTL" ] && kubectl delete configmap "$LOCK"
  sleep 15
done

Least-loaded lease acquisition: sort keys by current holder count (ghost holders whose pod no longer exists filtered out) and iterate in that order; atomicity stays in the kubectl replace with resourceVersion, the sort is only a preference. Also: Helm 4's bare --wait uses a kstatus watcher with an open bug that can report InProgress indefinitely; --wait=legacy polls directly. Under strategy: Recreate, per-image build triggers so a one-client fix does not restart every pod; unchanged images have their live tag re-supplied via --set because --reuse-values does not back-fill literal tags.

Verification. The SSA conflict reproduced live and cleared by matching the value; spread constraints patched onto running Deployments before being committed to the chart; the lock tested for atomic acquire, stale detection and release; the sort verified on synthetic registry data including ghost holders.

Generalisation. Under SSA every manual mutation claims field ownership. Resource scoring is not count spreading. Create-if-absent on the API server is a correct mutex primitive. First-fit allocation concentrates load; put fairness in the ordering and correctness in the compare-and-swap.

C. Data and storage

8. An incremental scan over a mutable timestamp index never finishes without an upper bound

Symptom. A delta aggregation that should take minutes runs for hours, re-processing documents it has already merged.

Mechanism. Aggregations are not snapshot-isolated. The scan walks the updated_at index from a watermark; concurrent writers bump updated_at on live documents, which moves them ahead of the cursor; the scan meets them again and re-merges. With continuous inflow the scan chases the head of the index instead of reaching an end.

Fix. Close the interval at the run's start time, and store that same value as the next watermark so anything written during the run belongs to the next delta:

run_start = now()
match = {"updated_at": {"$gte": watermark - timedelta(minutes=5), "$lt": run_start}}
# ... aggregate ...
save_watermark(run_start)

The 5-minute overlap below the watermark covers documents whose updated_at was set slightly before they became visible.

Verification. Unverified beyond the run completing; no test in the commit.

Generalisation. Any incremental scan keyed on a field that writers update needs a half-open interval [watermark, run_start). Not needed when the key is append-only (an insertion id, an immutable created_at).

9. Rebuilds replace, deltas merge; blobs live apart from state; caps are measured in the stored unit

Symptom. A full cache rebuild takes hours; every query on a state collection is slow regardless of projection; a payload store silently drops most inputs from some sources.

Mechanism. $merge upserts one document at a time, an _id lookup plus maintenance of five secondary indexes, millions of times on a rebuild. Response bodies of several hundred KB embedded in state documents raised the mean document size to ~36 KB, and the server fetches whole documents before projecting, so every non-covered query paid for bodies it never returned. A 200 KB cap on raw UTF-8 excluded any payload in a two-byte-per-character script above ~100k characters, and the skip logged at INFO every hundredth time.

Fix. Full builds write with $out (atomic collection swap, old one queryable meanwhile, indexes created once afterwards); deltas keep $merge. Bodies move to their own collection keyed by execution id, zlib.compress(raw, 6) as BSON Binary with byte counts, a TTL index on created_at as the retention policy, and a 12 MiB guard under the 16 MB document limit; the state document keeps a length only; the store runs after the state transition and swallows its own errors so it can never block the pipeline. The cap moves to the compressed size (256 KiB, roughly 1.5 to 2.5 MB raw) with an 8 MB raw guard before compressing; skips log at WARNING every fiftieth with a running skipped/total ratio. A second corpus keyed by entity rather than event, upserted on success, so its size is bounded by entity count and each document is the latest known-good input, with a 14-day TTL.

Verification. Compression round-trip and decoder parity offline; the rest unverified in the commits.

Generalisation. Bulk rebuilds should produce a fresh collection and index once. Large blobs are a tax on every query of the document that carries them. A size limit must be expressed in the unit that is actually stored, and a skip counter must be loud enough to be noticed in the first hour, not the first week.

10. str.splitlines() is not split("\n"), and stat() is not read()

Symptom. JSONL records uploaded to a remote worker fail to parse with "Unterminated string"; a reused worker processes a stale input file.

Mechanism. Python's splitlines() splits on every Unicode line boundary: U+2028, U+2029, U+0085, U+000C and more. Ingested text payloads legally contain those inside JSON string values, so one record became two half-records. Separately, the worker's network volume has lazy read consistency: stat() reports the final size while read() returns short data for minutes after the upload, and a reused pod still held the previous run's file under the same name.

Fix. .splitlines() to .split("\n") in all four readers. Uploads go to a temporary name followed by mv -f (atomic rename), then a remote check loops up to 20 times at 15 s intervals running a full json.loads over every line and comparing the line count to the local file, aborting on mismatch.

Verification. The remote full-parse loop is the verification; it fails the run rather than the analysis.

Generalisation. A line-delimited format is delimited by exactly one byte sequence; use the dumber splitter. On network filesystems, size is not readability; verify by parsing.

11. Measure what a cache saves before paying for it; then aggregate where the data lives

Symptom. A dashboard refresh streams an entire execution window into the API pod, copies payloads twice, materialises half a million dicts and OOM-kills a shared node; one stage alone takes 450 s.

Mechanism. Three separate costs. Round trips: a projected document was ~300 bytes, so batch_size(5000) filled 1.5 MB per reply against a 16 MB reply cap and bought ten times the round trips. Payload: a state_history: {$slice: -1} projection fetched an array element to recover a value the writer already sets atomically in the same update as the array push. Locality: the aggregation ran client-side over fat documents, including bodies it only measured.

Fix. Batch size raised to 50,000 and left to the reply cap. The history projection dropped after measuring state == last(state_history) agreement at 100% over a full day's window. Sizes computed server-side, with a type guard because one non-string value aborts the whole pipeline:

"body_bytes": {"$strLenBytes": {"$cond": [
    {"$eq": [{"$type": "$data.body"}, "string"]}, "$data.body", ""]}}

Then the whole refresh moved into the database: one pass projects ~20 scalar fields from the fat collection into a slim window collection keyed by execution id ($merge, whenMatched: replace, incremental by watermark with the same 5-minute overlap as entry 8, idempotent because the key is the execution id); "latest per entity" is derived with $group + $top {sortBy: {started_at: -1}} + $replaceWith $mergeObjects + $out, hash-group only, no sort stage; every downstream cache is an aggregate over the slim collections with allowDiskUse, capped lists via $topN. The watermark is honoured only when a stored schema integer matches the script's, otherwise a full rebuild is forced, because the delta path only rewrites moved documents and a new field would never back-fill. Derived fields are materialised once in the first stage, not per consumer; the 450 s stage was dropped rather than tuned, its last snapshot re-folded at no cost.

Verification. Measured before changing: dropping the projection raised fetch from 1,984 to 2,653 docs/s; on a 1.33 s round-trip link, batches of 1k / 5k / 20k gave 770 / 4,168 / 8,097 docs/s. Each stage timed and non-fatal, failures collected and reported at exit.

Generalisation. A cache that only shortens an indexed point lookup is not worth a second copy of every payload. Ship one slim projection, derive everything from it server-side, and version incremental caches so a schema change forces the full path. Audit polling loops for components that are mounted but never rendered: two of them were issuing live queries every 30 s for nothing.

12. Gate each step of a setup wizard on the production code path, and size the pod before the heavyweight client

Symptom. A configuration passes its setup check and fails in production; the first heavyweight-client probe inside the API pod is OOM-killed.

Mechanism. The check and production used different code. And the heavyweight client adds 400 to 800 MiB to a process whose limit was 512 MiB.

Fix. A four-step state machine (Source → Access → Extraction → Save, canNext = step === 0 || passed[step], loading a saved config resets both) where every green check is produced by the same functions production runs: the access step replays the exact access strategy (lightweight client; heavyweight client to obtain credentials then lightweight replay with them; or heavyweight client throughout); the extraction step replays the production transform on the cached response. The probe classifier is two lines and deliberately dumb:

blocked = status in (403, 429, 503) or (len(body) < 8000 and BLOCK_RX.search(body[:20_000]))
ok      = 200 <= status < 300 and len(body) > 4000 and not blocked

The pod's limits moved to 2 CPU / 2 GiB before the first launch; the client, its driver and its fingerprint library are pinned together at one protocol revision. A config-write validator allow-lists keys and types (_INT_KEYS, _BOOL_KEYS, chain.keys ⊆ {steps, result, vars, cred_refs}) and is regenerated from the consumer's enums, because an allow-list that drifts from the consumer silently rejects valid production shapes. A model's self-reported confidence is rendered as the weakest signal on a card, in muted type with the tooltip "not verified"; verified hit rates decide.

Verification. Frontend build plus backend import on every change; probe rule exercised against known blocked and known good responses.

Generalisation. A check that does not run production's code proves production will not run. A heavyweight client inside an API pod is a resource-class change, not a dependency.

D. One generative slot between deterministic gates

Seven entries on a loop that asks a language model to propose a replacement query expression (a path predicate over a tree-structured document) when an existing expression stops yielding a field, and that trusts nothing the model says until deterministic code has run it. The architecture rule every entry depends on: deterministic code before and after exactly one model call, each stage a subprocess behind a dispatcher, and a single writer (a human approval endpoint) for live configuration.

13. Triage by aggregation, cluster by structure, send a fragment

Symptom. A model asked to repair expressions on raw failed documents answers on almost nothing, or on everything and mostly wrongly, and burns its context on index documents, boilerplate regions and executable payloads.

Mechanism. Three problems before the model: most failures are not fixable by a new expression at all (access denied, dead URL, upstream error); the fixable ones repeat the same few templates thousands of times; and a document is mostly not the thing you want from it.

Fix. Triage as one aggregation with an exclusive $switch, first rule wins, bodies never decoded: blocked if status ∈ {403, 429, 503, 520}; dead_url if ∈ {404, 410}; infra if status ≥ 500 and no body; fixable if the transform failed with a body and a 2xx or null status; else other; an invariant asserts the buckets sum to the total. Under half of all failures were fixable. Clustering per expression: sample 30 failed documents and fingerprint each as a hard key {block_stub | has_structured_block | size_bucket} (size edges 2k / 20k / 100k / 500k characters) plus the vocabulary of its structural attribute tokens, i.e. the set of labels the template author attached to nodes; greedy single pass, a document joins the first cluster in its hard-key bucket whose vocabulary has Jaccard similarity ≥ 0.85 with its own and widens the cluster's set to the union, otherwise opens a cluster. Content varies within a template; the label vocabulary does not. Clusters under 5% share are dropped; document kind (single entity, index, blocked, not found) is decided by ordered rules, the decisive one being the label of the top-level container, then counting repeated sibling blocks: index = blocks ≥ 10 ∨ (paginated ∧ blocks ≥ 4) ∨ values ≥ 5. An index document with twenty copies of the target attribute passes any single-match test; counting catches it. Two orders of magnitude fewer documents go to the model than failures came in.

Context construction is a pruning function P: document → window, in three stages with fixed bounds. Denoise. Remove subtrees that carry no semantics for the task (presentation, comments, vector graphics, executable payloads), except payloads that serialise application state, because in client-rendered documents that serialisation is the only copy of the target value; hard cap 120k characters. Localise. Keep a small header window (document title, the first two structured-data blocks ≤ 4k each, ≤ 12 metadata entries, ≤ 8k in total) and one target window. Candidate anchor nodes are enumerated in a fixed priority order of attribute patterns (≤ 60 per pattern), kept only if their text or value attribute matches the field's value shape, and rejected if any of their 8 nearest ancestors is a boilerplate region; the window then grows upward from the anchor until it holds ≥ 1,200 characters and continues while the parent stays ≤ 25,000. Primary window ≤ 30k characters; a sibling document's window ≤ 18k; if localisation yields under 800 characters the whole denoised document is sent instead. Orient. The anchor's ancestor path (≤ 6 levels, each node as its label plus identifier or its first two attribute tokens) is supplied as a separate line, so the model can express a location structurally rather than by guessing. Measured: the windows total 27% of the denoised size.

Verification. Triage invariant on every run; clustering output inspected per expression (most single-mode, a minority with two or three templates); the benchmark series in entry 18 measures the effect of each context rule.

Generalisation. The first value-shaped node in a document is usually boilerplate. Cluster on structure, not content; count, do not match; give the model the fragment a human would look at, plus the path that tells it where the fragment sits.

14. Reasoning expands to fill its pool: cap the thinking block, not the total

Symptom. With extended reasoning enabled, 19 of 23 benchmark documents return empty with finish_reason = length after ~530 s each. Two identical runs at temperature 0.1 disagree on 4 of 46 field slots, moving a headline number by ±2.

Mechanism. max_tokens is one shared pool for reasoning and answer; a reasoning model given 6,000 tokens uses them all thinking and has none left to answer. Sampling at 0.1 makes the evaluation non-reproducible at the granularity the benchmark reports.

Fix. Two separate controls: the shared pool stays at 2,000 while a server-side hard stop closes the thinking block after a fixed budget:

extra_body = {"chat_template_kwargs": {"enable_thinking": True},
              "thinking_token_budget": 512}          # useful range 256–768
temperature = 0.0; seed = 20260814; max_tokens = 2000
# server: --reasoning-parser ... --reasoning-config {"<think>","</think>"}
raw = choice.message.content or getattr(choice.message, "reasoning_content", "")

Empty content falls back to the reasoning field; finish_reason, output tokens, elapsed seconds and whether a retry happened are recorded per document. A larger code-instruct model used later for escalation needs the reasoning parser switched off, or its entire answer lands in reasoning_content.

Verification. Unbounded thinking at 1,200 and 6,000 tokens: 19/23 empty. Capped at 512: 11 of 11 fields usable. Greedy decoding with a seed: identical answers on rerun, 43 of 46 slots deterministic across versions.

Generalisation. A non-reproducible difference is not a result. Budget reasoning as its own resource with its own stop; a total-token cap only decides which half of the output you lose.

15. One mechanical feedback round; the model mostly withdraws, and withdrawal is the win

Symptom. A model prompted to repair answers on every field, and the answers fail on the very document they were written against.

Mechanism. The model cannot execute what it proposes. A local evaluator can, in milliseconds, with the same query engine the consumer uses.

Fix. After parsing the answer, run every proposed expression locally and return the first applicable fault from an ordered list: does not compile → matched nothing → matched N > 1 ("the consumer takes the first match") → bound to a single instance (an identifier of three or more digits, or a positional predicate) → coupled to an attribute that encodes state rather than structure → categorical field returned a unit-only or label-only string → numeric field's string has no digit. When a known-good document rides along, two more faults: zero matches on it, or a value different from the reference recorded there (numeric within 0.01, categorical exact). If any fault exists, append the assistant turn and one user message ending "null is a correct answer", ask exactly once, keep the revision only if it parses. Escalation to a three-times-larger code-instruct model receives the base answer as an assistant turn plus the faults, with no thinking and no second round; the rule to escalate is "the evaluator rejected the first model's final answer, or the first model withdrew".

Verification. On the fixed benchmark, one feedback round kept the same eight good expressions while junk fell from 12 to 3 and declines rose from 3 to 19. The escalation model on the easier slice fixed 22% of bad fields and broke working ones; on the harder slice it fixed none. Not adopted.

Generalisation. Put the evaluator, not a second model, in the loop; the model's contribution is bounded by the fragment it is shown, so a bigger model on the same fragment repeats the same fault classes. Design the loop so "I withdraw" is a first-class, rewarded answer.

16. A verdict ladder, combinator semantics that match the consumer, and a trial that names its two questions

Symptom. A proposal scoring 33 of 33 "both ways" is returning a label on every document; a candidate with 6.7% cluster share overwrites three larger repairs for the same field; a row that one producer wrote retires a row another producer needed.

Mechanism. Presence counts cannot tell a value from a label. An upsert keyed on (expression, field) keeps whichever cluster ran last. Two producers writing one key cannot coexist.

Fix. Every proposal replays through the production parser and gets one verdict in fixed order: invalid → no_value → wrong_kind → document_specific → ambiguous → usable, with cross-validation on the expression's other sampled documents demoting zero cross-hits to document_specific. Publishing runs in two passes: verify everything, then merge per (expression, field): identical candidates merge with impact summed; candidates rank by verdict, then cross-hits, then share. For the numeric field the top two candidates form a chain, and the chain is checked with the consumer's semantics, first candidate in order whose text parses as a number wins, which is not a union of matches; the chain is usable only if it hits on every sampled document and every member is usable. The categorical field gets no chain, because there the same syntax means union. The unique index became (expression, field, source) so two producers can hold proposals for the same field at once. The trial replays current versus proposed on 50 failed documents filtered to single-entity kind and 50 known-good documents: a hit is a non-empty, right-kind value; losses = current hit and proposed miss on the failed set; regressions = the same on the known-good set; verdict unverifiable → regression → gain → loss → no_gain, and the two sets are labelled separately in the UI because two measurements under one label hide the important half. A top_values distribution exposes "33 identical label strings".

Verification. The overwritten case now shows a chain hitting 8 of 8 with summed impact; its trial went from 0/50 to 50/50. Rows restored after the index change; the old index dropped on the next publish.

Generalisation. Verify with the consumer's parser and the consumer's combinator semantics, never a stand-in. Key stored proposals by every dimension that can legitimately differ. Report gains and regressions as two numbers.

17. A validation set drawn only from failures cannot detect regressions

Symptom. Proposed expressions pass every check (unique match, plausible value, no positional anchors) and still break the field on most documents once published.

Mechanism. The loop validated a proposal only against documents that had failed. Two classes of wrong proposal are invisible there: one written for a minority template that matches nothing on the majority layout, and one that picks a neighbouring node yielding a plausible but different value. Only documents where the current configuration works can expose either.

Fix. A success gate at publish time and inside the loop, run over a sample of known-good documents that carry the value production extracted from that exact body:

got = evaluate(doc.body, final_expression, field).get("value")
if not got:                      lost += 1
elif abs(float(got) - float(doc.reference)) > 0.01: mismatch += 1
if (lost + mismatch) and verdict in ("usable", "ambiguous"):
    verdict = "regressive"       # counts and up to 3 mismatch samples stored on the row

Sample size is set by the miss rate the gate must catch: a proposal that breaks 5% of known-good documents escapes a gate of 25 with probability 0.9525 ≈ 0.28 and a gate of 50 with 0.9550 ≈ 0.08, so the known-good sample was raised to 50, equal to the failed sample. Three companions: before proposing, run the current expression over the sampled failed documents and mark the proposal current_works if it yields on all of them (the failure was on another field); treat a human rejection as a terminal state in the upsert filter, suppressing an identical re-proposal and re-filing a different one with the rejection history attached; and surface the null outcome, so an expression whose failed documents are all of the wrong kind produces one policy row asked once (status $nin [approved, rejected]) instead of reappearing with thousands of "failures" every run.

Verification. Synthetic documents: minority-template and wrong-node proposals draw faults, correct ones stay silent, an empty corpus is silent. Rejection logic checked against a decision table (same candidate suppressed, different candidate re-filed with history, approved untouched, pending refreshed). A separate read-only script measured whether the worker's parser implementation and production's disagreed on proposals: 3.2% of decisions depended on the parser, 28% were misses under both, so the dependency was not added and the effort moved to the proposal step.

Generalisation. A repair loop needs labelled positives from the same distribution as its failures, sized by the regression rate it must catch; human decisions must be terminal states in any idempotent regeneration; "correctly produced nothing" must be observable as a decision. Measure a suspected cause before paying for its fix.

18. Evaluate by re-scoring frozen inputs, and rank by cost per usable output

Symptom. Two runs a week apart cannot be compared: the evaluator changed, the inputs changed, the temperature was non-zero.

Mechanism. A benchmark whose oracle moves measures the oracle.

Fix. Ground rules written down and enforced by tooling: re-score rather than re-read (a report command recomputes every historical verdict with today's evaluator); same frozen input set, temperature 0, fixed seed; the production parser is the oracle; documents of the wrong kind leave accuracy denominators; unparseable output counts under stability, not accuracy. Metrics with formulas: precision = usable / proposed (declines excluded); yield = usable / (documents × fields); decline and wrong-decline rate; hold-on-siblings = cross_hits / cross_documents; gain and loss on failed documents; regression on known-good documents is a gate, measured and required to be zero; validity and agreement with a reference (numeric within 0.01 at the gate, 0.005 in the master comparison); parser drift; latency as median and tail seconds per document, output tokens, runaway rate (hit the cap unfinished), feedback-round frequency; determinism as identical answers on rerun; confidence calibration. Everything reported as per-source distributions, never a mean. Ranking rule: cost per usable output, tie broken by precision. The evaluation set is versioned per cycle, stored not re-fetched, with a stated trap per scenario, a negative document where null is correct, and at least two layouts and one known-good document per source.

Verification. The series this produced on 23 fixed documents: generic prompt 3/4 usable but answering on almost nothing; repair framing 6/15; focused fragment plus sibling 8/20; two more prompt rules 8/14; one feedback round 8/11; unbounded thinking 0/0; capped thinking 11/11; temperature 0 plus seed 10/11, adopted. In production over three growing input sets the known-good lane held at 81 → 77 → 76% and the failed-document lane at 51 → 49% after a stricter regression gate. Of 442 non-usable proposals, 138 matched nothing, 163 matched several, 58 were positional, 39 returned non-value text, 7 did not compile, 12 were locale parsing bugs (74,95 read as 7495); 301 were dropped automatically before any human saw them. Passing numeric proposals equalled the reference value in 98.5% of cases.

Generalisation. Freeze the inputs, pin the decoder, version the oracle, and rank by the number you would actually pay for. Anything else compares runs to themselves.

19. Port semantics, not syntax: the PCRE U flag

Symptom. Hundreds of legacy extraction patterns fail to compile or capture entire documents when moved from PHP preg_* to Python re.

Mechanism. Patterns of the form @open(.+)close@Us rely on the PCRE U flag, which inverts quantifier greediness globally. Python has no equivalent, so (.+) stays greedy and a bounded capture swallows everything to the last closing delimiter.

Fix. Parse delimiter and flags, map s/i/m/x, and honour U by rewriting the greediness of every quantifier outside escapes and character classes (+ to +?, +? to +, counted {m,n} handled the same way). Group 1 is stripped of nested markup and whitespace-collapsed before numeric cleaning. The strategy is ordered after structured data and the primary expression, and the preference flag mirrors the primary one so a source configured only with patterns is not shipped with an empty configuration.

Verification. Every pattern compiles; live re-validation moved a large majority of the previous invalid results to ok_regex, with a handful of genuine no-matches left.

Generalisation. A single unhonoured flag changes the language, not the dialect. When adding a strategy, audit every branch written before it existed.

E. Sticky sessions and upstream identity

20. A placeholder that is never substituted is not a no-op; it is a shared identity

Symptom. Hundreds of logically independent client sessions observed leaving a gateway through one upstream address; two sessions configured for different regions share an address; "move on flag" has no effect.

Mechanism. The gateway credential template contained {session}. One request path substituted it; another never did, and callers percent-encoded the credential before the substitution check, so "{session}" in url was false and the gateway received the literal %7Bsession%7D. The gateway treated that literal as one session id for everyone. A second bug in the same family: the token minted from host#stream only mapped . to -, so # entered the credential URL as a fragment delimiter and the client rejected every request with "Unsupported proxy syntax".

Fix. Recognise the placeholder raw and encoded, case-insensitively, at every step it passes through; resolve it per namespace (host#stream) so every piece of per-session state (token store, client fingerprint, session token, breaker) is keyed together. Two token patterns on purpose, one for minting and one for validation, since a single pattern would flag every minted token and re-mint per request, destroying stickiness:

_SLUG_UNSAFE  = re.compile(r"[^a-z0-9]+")   # minting: collapse to a slug
_TOKEN_UNSAFE = re.compile(r"[^a-z0-9-]")   # validation: re-mint stored tokens in place

Two related bindings: an access token issued by the upstream is bound to source address and client fingerprint, so the token store is dropped when the pinned fingerprint is missing or when two fingerprint dimensions contradict each other (the declared client family and the transport-layer family must agree; a contradiction is a positive signal of automation, not a degraded request); and when merging token lists from incremental renewals, dedupe by name keeping the latest expires, because assignment order otherwise keeps the older token bound to an address that has since rotated away.

Verification. Measured on the gateway: the literal placeholder resolved to one address; a per-host token to a different one. The reassignment mode shipped with nine async tests covering every failure path falling back to a fresh session.

Generalisation. Match placeholders after every encoding step they pass through. A documented invariant on identifiers is not an invariant until enforced at write and at read. Identity has to be coherent across address, token store and every fingerprint dimension, or it is theatre.

21. Rotation modes and pool bounds

Symptom. A "move the session to a fresh upstream address" operation ping-pongs between two already-flagged addresses.

Mechanism. Three ways to react to a flagged address: mint a new session; reconnect the bound tunnel (rotate: a genuinely new address on the same pod, slow, disturbs other sessions there); or reassign to another already-connected pod in the same region (fast, token unchanged, no reconnect). Reassign only cycles among existing pods, so on a two-pod pinned pool its reachable address set has size two; freshness on a small pool requires reconnection. The pinned-pool variant for upstreams that limit per address admits an address through three steps (echo the address un-pinned, rebuild the credential with the pin and echo again requiring the same address, fetch requiring the configured status and no challenge markers), holds leases in a sorted set scored by available_at, evicts only on the configured flag statuses (a 404 is a resource-level error and must not count against an address), and draws the rotate-every-N threshold once per cycle, because re-rolling per request makes the effective threshold the minimum of N draws.

Fix. Rotation mode is a per-upstream setting with a comment recording why it was last flipped; every new mode falls back to a fresh session on any failure path (no base URL, 404, non-200, unreachable, no live token).

Verification. Rendered configurations diffed against HEAD so exactly the intended upstreams change; the reassign fallbacks unit-tested.

Generalisation. Pod-hopping is bounded by pool size. Never count resource-level errors against an address. A threshold drawn per event is not the threshold you configured.

22. Isolation multiplies the number of identities you must keep alive

Symptom. Splitting a queue into N isolated streams on one region makes throughput worse, twice, within two days.

Mechanism. A stream is one queue drained by its own Deployment plus a namespace host#stream isolating token store, access token, session token, fingerprint pool and breaker. Streams on the same region share one address's per-address rate budget while each still needs its own access token, and the token-acquisition step runs one process-wide; N streams cost N acquisitions per renewal cycle against a fixed acquisition throughput. Six tokens on one region were measured landing on two addresses, so the split bought failure isolation and independent sizing, not address diversity.

Fix. Stream count moved into the queue registry so the setup script derives shards from one source; back to a single queue with a per-request random delay as the only per-address pacing; disabled configuration left commented in place with the reason next to it, so re-enabling is an uncomment rather than an excavation.

Verification. Rendered configs diffed against HEAD; Helm names checked one-for-one against registered shards.

Generalisation. The binding constraint on isolation is the number of identities the acquisition path can sustain, not pod count. Keep the revert in place.

The month's single most reusable mechanism: a container restart reuses the network namespace, the sandbox's resolv.conf and every pod-scoped volume. Four of the twenty-three entries (duplicate iptables and ip rules, the emptied resolv.conf, the logout-on-restart storm, the lease-holder ghosts) are the same mistake: a start-up script written as if it runs once. Make every mutation at start idempotent, and every cleanup conditional on deletionTimestamp.

F. Geometry

23. Positions to rotations without inverse kinematics

Symptom. A skinned character driven from 23 joint positions per frame drifts at the wrists; one knee lands exactly and the ankle below it lands 30 cm away.

Mechanism. Rotation alone cannot correct bone length, so error accumulates down each chain. The 30 cm ankle was a cache: a bone's world matrix was cached when its own position was read, before its rotation was solved, and its child then composed against the stale parent.

Fix. Per bone, inherit the parent's rotation change, swing the rest direction onto the data segment with setFromUnitVectors, take roll from an explicit hint (hip line, shoulder line, bend plane) blended to the inherited roll when the hint's perpendicular component falls below 0.12 of unit length; re-length limb bones to the data segment each frame, reading the segment head from where the bone actually is; drop the cache entry the moment a bone is solved. Baked animations go through the same solver rather than copying quaternion tracks between rigs with different bone frames.

Verification. Headless: every position in the database on four rigs, limb joint error 0.0 cm, roll error 0° wherever the hint is strong, every clip poses a standing body. Full account in the retargeting post.

Generalisation. In a top-down solver a cached transform is valid only after its node is finalised. When the target can change length, stretching beats IK.

Open questions, stated so they can be wrong

  • Every restart-in-place failure this month would have been prevented by a single rule: "no start-up mutation without a matching delete-until-absent". Claim: a linter that flags iptables -I, ip rule add and echo >> /etc/resolv.conf without a preceding delete loop would have caught four of twenty-three entries at review time.
  • Claim: the closed-interval rule for incremental scans (entry 8) applies to every "process since watermark" loop over a mutable field, including log tailers keyed on modification time. A counterexample would be a scan where writers only ever decrease the key.
  • Claim: with a deterministic evaluator in the loop, a model's repair rate is bounded by the fragment it is shown, not by its size; a model three times larger on the same fragment reproduced the same fault classes (entry 15). Falsified if a larger model on an unchanged fragment fixes the "matched several nodes" class, which is the largest one.
  • Claim: the sample-size arithmetic of entry 17 (escape probability (1−p)n) is the right sizing rule for any publish gate, and the right n is the one that makes the escape probability lower than the human review rate. This month's 50 was chosen to match the failed sample, not derived; the derivation is next month's work.
