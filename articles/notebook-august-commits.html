Notebook, August: 23 rules, each with its mechanism

Distilled from a month of commits and written for whoever meets the same situation next. Every entry has the same shape: when you see this, do this, because of this, check it this way, and here is where it stops applying. Nothing about where it happened.

I Ierofantis · 24 min read · monthly notebook, from git history
📓

Provenance in one line: the rules below come from the reverts, second fixes and design changes of one month across eight repositories; each was reproduced from the diff before it was written down. Numbers are defaults that worked, not laws.

A. Networking inside containers

1. If a process takes over the default route, give replies a way back

When. A pod that runs a tunnel client reports Connected, traffic from inside the pod works, but nothing in the cluster can open a TCP connection to it. Health checks on its listening ports time out. Your first guess is a firewall DROP.

Do. Before connecting the tunnel, record the interface address and its original gateway; after connecting, add a source-based policy rule for that address into its own table, idempotently:

ETH0_IP=$(ip -4 addr show eth0 | awk '/inet /{sub("/.*","",$2); print $2}')
ETH0_GW=$(ip route | awk '/default via/{print $3; exit}')
# ... connect the tunnel ...
while ip rule del from "$ETH0_IP" table 100 2>/dev/null; do :; done
ip rule add from "$ETH0_IP" table 100
ip route replace default via "$ETH0_GW" dev eth0 table 100

Use awk, not grep -P: busybox images fail the latter with a non-zero exit, and an empty variable silently produces a rule that matches nothing.

Why. Tunnel clients install fwmark policy routing at a low priority number (for example not from all fwmark 0xca6c lookup 51820 at priority 9). Any destination-based exception you or the base image added at a higher number is never consulted. A SYN arrives on eth0; the SYN-ACK is routed into the tunnel and never returns. From outside this is indistinguishable from a DROP.

Check. Apply the routing change alone, touch nothing in the firewall, probe from the peer. If reachability returns, the diagnosis was routing. Test one hypothesis per change.

Limits. Not needed if the tunnel client itself exempts the interface's subnet at a priority lower than its own catch-all. Applies equally to clients that replace the default route outright.

2. Treat every start-up mutation as one that will run again in the same namespace

When. A pod with hundreds of container restarts starts failing health checks while its actual service is fine; latency on its ports grows with the restart count.

Do. Delete until absent before every insert. iptables -D removes one matching rule per call and fails when none remain; ip rule del behaves the same:

while iptables -D INPUT -p tcp --dport 8118 -j ACCEPT 2>/dev/null; do :; done
iptables -I INPUT -p tcp --dport 8118 -j ACCEPT
while ip rule del from "$ETH0_IP" table 100 2>/dev/null; do :; done
ip rule add from "$ETH0_IP" table 100

Why. Under restartPolicy: Always a container restart reuses the pod sandbox: the network namespace, the emptyDir volumes and /etc/resolv.conf all survive. iptables -I and ip rule add have no uniqueness constraint; a start script that runs them unconditionally accumulates one copy per restart (over a thousand INPUT rules on one pod), and netfilter evaluates chains linearly per packet.

Check. Count rules on a long-lived pod before and after. In an unprivileged test namespace, run the script five times: the old version leaves five copies, the new one leaves one.

Limits. Also covers routes, resolv.conf edits and any file under a pod-scoped volume. Does not cover a pod recreation, which is a fresh namespace.

3. Enumerate every resolver path in the pod before trusting a DNS allow-list

When. curl inside the pod resolves and fetches; the same URL through a daemon in the pod returns "Host Not Found". Or: after a container restart the pod has no nameserver at all and crash-loops on its first fetch.

Do. Make daemons that resolve on their own follow the system resolver, rewritten at runtime from what the tunnel client wrote:

TUNNEL_DNS="$(awk '/^nameserver/{print $2; exit}' /etc/resolv.conf)"
sed -i "s/^nserver .*/nserver ${TUNNEL_DNS}/" /etc/proxy/proxy.cfg

For the empty-resolv.conf case, have your pre-up hook re-inject the pod's own dnsConfig resolvers, never the cluster DNS service address.

Why. A daemon with a hardcoded nserver sends UDP 53 directly; a tunnel client's firewall typically rejects outbound 53 except to loopback, even with its fail-closed mode off, while libc's getaddrinfo goes through /etc/resolv.conf to the client's own resolver on loopback, an allowed path. Same host, two resolvers, one blocked. Separately, wg-quick runs resolvconf -d wg0 on shutdown and empties resolv.conf; kubelet writes that file only at sandbox creation, so a restarted container inherits the empty one. Under dnsPolicy: None plus a NetworkPolicy that denies in-cluster DNS egress, the cluster DNS address is unreachable by design.

Check. Reproduce in local Docker outside the cluster; then hit the daemon's health endpoint by hostname. For the resolv.conf case, write the resolvers into the crash-looping pod by hand: it should come up on the next restart.

Limits. Only relevant when something in the pod resolves without libc: proxies, custom DNS clients, some language runtimes with their own resolver.

4. Poll the state you need; treat a CLI exit code as "request accepted"

When. Every start-up command returned 0 and the service is permanently Disconnected.

Do. Retry prerequisites until their state confirms (for example an enable step, up to 5 × 2 s, fatal if never confirmed); follow every connect with a poll of the status output (15 × 1 s, status | grep -q Connected), ignoring the exit code; change daemon settings only in the disconnected state and read them back with the matching get.

Why. CLIs that talk to a daemon asynchronously return when the command is accepted. A connect that is a documented no-op unless a mode is enabled still exits 0; a setting toggled after connect can trigger a reconfigure that never converges.

Check. Kill the daemon mid-sequence and confirm the script fails loudly instead of proceeding green.

Limits. Synchronous CLIs that block until the state is reached do not need this; read their documentation to know which kind you have.

B. Control loops and orchestration

5. Give probes hysteresis; give expensive client-triggered actions a breaker and single-flight

When. Healthy targets flip UNHEALTHY and back within one probe cycle. A recovery endpoint takes minutes, every caller who hits the failure triggers it again, and the process starves or OOMs.

Do. Require 2 consecutive failures to flip, reset on any success, log transitions rather than samples, and keep UNKNOWN on a single failure. Set an explicit probe timeout (Kubernetes default is 1 s; 5 s is a sane floor when the probe shares an event loop with real work). Wrap the expensive action:

cooldown = min(base * 2 ** (failures - 1), cap)      # e.g. 5 s -> 300 s
if target in in_flight or now < cooldown_until[target]:
    return None                                        # refuse; no await between check and add
in_flight.add(target)
# on failure: drop the binding and re-pick with exclude={target}; serve the old
# target rather than returning 503; at most one recovery attempt per request

Why. A single-shot probe cannot distinguish a dead target from a coroutine that was scheduled late. Anything expensive that clients can trigger concurrently becomes a self-inflicted denial of service without single-flight.

Check. Unit tests: one failure does not flip a healthy target; success resets the counter; cooldown opens and backs off exponentially; a concurrent caller is refused; the re-pick excludes the failed target. Export health, consecutive failures and a transitions counter to Prometheus, and delete series for targets that disappear: gauges do not expire on their own.

Limits. Hysteresis hides real flapping for one extra cycle; do not raise the threshold to cover for a contended loop, fix the loop.

6. Never put external and internal recovery on the same cadence; log out only on real termination

When. The liveness probe kills a container at the exact moment its own reconnect loop starts, every time. Every restart re-authenticates against an external API, and a rate limit trips.

Do. If a container self-heals after k failures at period p, set the liveness probe to fail no earlier than about 2kp (for example internal 3 × 30 s, probe failureThreshold: 8). Keep login state in a pod-scoped emptyDir mounted at the client's state directory, seeded from a .default copy in the image when empty (a plain mount would shadow reference data the client needs), and gate login on a local status query. Run cleanup that costs something only when the pod is really going away:

pod_is_being_deleted() {
  [ -n "$(kubectl get pod "$POD_NAME" -o jsonpath='{.metadata.deletionTimestamp}')" ]
}

Why. Two recovery loops with identical thresholds reach them simultaneously and the external one wins. A preStop hook fires on a liveness-triggered kill inside a still-alive pod, so "log out on exit" runs on every restart and turns restart storms into auth storms. Note that a script running as PID 1 gets no default signal handling; trap 'exit 0' TERM is required for any EXIT trap to fire at all.

Check. On a throwaway cluster, confirm deletionTimestamp is set on delete, eviction and Recreate rollouts and empty on a liveness kill. Trace pod events to see which loop fired first.

Limits. emptyDir survives container restarts, not pod recreation. If the client has no internal loop, leave the probe tight.

7. Declare ownership and placement; build mutexes on create-if-absent

When. helm upgrade refuses with "conflict with 'kubectl' … .spec.replicas". New replicas all land on one node. Two CI runs from one push and the second dies at 0 s. One credential holds more leases than its cap while another is unused.

Do.

  • Under Server-Side Apply, never kubectl scale a managed object; change the value in the chart and let the declarative owner apply it.
  • Spread by count, softly, so a cordoned node never strands pods Pending: 
    topologySpreadConstraints:
  - maxSkew: 1
    topologyKey: kubernetes.io/hostname
    whenUnsatisfiable: ScheduleAnyway
    labelSelector: { matchLabels: { component: your-component } }
  • When the CI server's concurrency control misbehaves, take a lock on the API server, scoped to the step that touches the shared resource, with a TTL and stale takeover, released in an if: always() step: 
    until kubectl create configmap "$LOCK" --from-literal=holder="$RUN" \
        --from-literal=acquired="$(date -u +%s)"; do
  AGE=$(( $(date -u +%s) - $(kubectl get cm "$LOCK" -o jsonpath='{.data.acquired}') ))
  [ "$AGE" -gt "$LOCK_TTL" ] && kubectl delete configmap "$LOCK"   # e.g. TTL 1800 s, max wait 1500 s
  sleep 15
done
  • Allocate shared credentials least-loaded first: sort by current holder count with ghost holders (pod gone) filtered out, iterate in that order, and keep atomicity in the compare-and-swap (kubectl replace with resourceVersion), not in the sort.
  • Pin readiness strategy explicitly across tool major versions (helm --wait=legacy where the watcher hangs), and under strategy: Recreate trigger builds per image so a one-component fix does not restart every pod; re-supply unchanged images' live tags via --set, because --reuse-values does not back-fill literal tags.

Why. SSA assigns a field manager to every mutation and refuses a conflicting owner. The default scheduler scores free resources, not pod counts, so freeing space on the crowded node puts replacements straight back. Create-if-absent on the API server is atomic. First-fit allocation fills the first slot forever.

Check. Reproduce the SSA conflict, then match the value and watch it clear. Patch the spread constraint onto a running Deployment before committing it. Test the lock for atomic acquire, stale detection and release. Run the sort on synthetic registry data that includes ghosts.

Limits. The ConfigMap lock is correct for a handful of writers; for high contention use a proper lease object with renewal.

C. Data and storage

8. Bound every incremental scan over a mutable key with a half-open interval

When. A delta job over an updated_at index that should take minutes runs for hours and re-processes documents it already handled.

Do. Close the interval at the run's start time and store that time as the next watermark:

run_start = now()
match = {"updated_at": {"$gte": watermark - timedelta(minutes=5), "$lt": run_start}}
# ... aggregate ...
save_watermark(run_start)

The overlap below the watermark (a few minutes) covers documents whose timestamp was assigned slightly before they became visible.

Why. Aggregations are not snapshot-isolated. Writers bump the key on live documents, which moves them ahead of the cursor; the scan meets them again. With continuous inflow it chases the head of the index instead of reaching an end.

Check. Run the job under live writes and confirm wall time is bounded by the interval's size, not by the inflow rate.

Limits. Unnecessary when the key is append-only (insertion id, immutable created_at). Required for anything writers update, including file modification times.

9. Rebuild with replace, delta with merge; keep blobs out of state documents; cap in the stored unit

When. A full cache rebuild takes hours. Queries on a state collection are slow whatever you project. A blob store silently drops most inputs from some sources.

Do. Write full builds with $out (atomic collection swap, old one queryable meanwhile, indexes created once afterwards) and keep $merge for deltas. Move large payloads to their own collection keyed by the event that produced them: zlib.compress(raw, 6) as binary with byte counts, a TTL index as the retention policy, a guard under the document limit (12 MiB under a 16 MB cap), the state document keeping only a length. Store after the state transition, and swallow store errors so the store can never block the pipeline. Express any size cap in the unit you store (256 KiB compressed, with an 8 MB raw guard before compressing) and log skips at WARNING with a running skipped/total ratio. When you need "current state per entity", key a second corpus by the entity, upserted on success, with its own TTL: its size is bounded by entity count and each document is the latest known-good input.

Why. $merge upserts one document at a time, an _id lookup plus every secondary index, millions of times on a rebuild. The server fetches whole documents before projecting, so a blob inside a state document taxes every non-covered query of that document. A cap on raw UTF-8 excludes any two-byte-per-character script above half the nominal size; a skip logged at INFO every hundredth time is invisible.

Check. Compression round-trip and decoder parity offline; mean document size before and after; the skip ratio visible in the first hour of a run.

Limits. $out replaces the whole collection; if consumers read during the build they see the old one, which is the point, but do not mix it with concurrent deltas into the same collection.

10. Split line-delimited formats on exactly one byte sequence; verify uploads by parsing, not by size

When. JSONL records arrive corrupted ("Unterminated string") on a remote worker. A reused worker processes last run's file under the same name.

Do. Use split("\n"), never str.splitlines(), for JSONL. Upload to a temporary name, then mv -f (atomic rename). Then, on the remote side, loop (20 × 15 s worked) running a full json.loads over every line and comparing the line count to the local file; abort the run on mismatch.

Why. splitlines() splits on every Unicode line boundary (U+2028, U+2029, U+0085, U+000C, …), which text payloads legally contain inside JSON strings. Network volumes can have lazy read consistency: stat() reports the final size while read() returns short data for minutes.

Check. Feed a record containing U+2028 through both splitters. Upload a large file and read it back immediately; compare byte counts and parse results over time.

Limits. If your format really is defined on Unicode line boundaries, the dumb splitter is the wrong one; JSONL is not.

11. Measure what a cache saves before building it; then aggregate where the data lives

When. A refresh job streams a whole time window into an API pod, materialises hundreds of thousands of dicts, and OOM-kills a shared node; one stage dominates the runtime.

Do. First measure: batch size against reply cap (a 300-byte projected document at batch_size(5000) fills 1.5 MB per reply against a 16 MB cap, ten times the round trips; 50,000 and let the cap bound it), whether a projection fetches something the writer already stores atomically elsewhere (drop it after measuring agreement at 100%), and whether the cache shortens anything but an indexed point lookup (then it is a second copy of every payload for nothing). Then move the work server-side: one pass projects ~20 scalar fields from the fat collection into a slim window collection keyed by event id ($merge, whenMatched: replace, incremental by watermark as in rule 8, idempotent because the key is the event id); derive "latest per entity" with $group + $top {sortBy: {started_at: -1}} + $replaceWith $mergeObjects + $out, hash-group only, no sort stage; build every downstream view as an aggregate over the slim collections with allowDiskUse and $topN for capped lists. Guard server-side string functions against type errors, because one wrong value aborts the pipeline:

"body_bytes": {"$strLenBytes": {"$cond": [
    {"$eq": [{"$type": "$data.body"}, "string"]}, "$data.body", ""]}}

Version the incremental cache: honour the watermark only when a stored schema integer matches the script's, else force a full rebuild. Materialise derived fields once in the first stage. Time every stage, keep them non-fatal, and drop the outlier stage rather than tuning the job around it. Audit the UI for components that are mounted but never rendered and still poll.

Why. The delta path only rewrites moved documents, so a new field never back-fills without a forced full run. Client-side aggregation pays transfer and memory for bodies it only measures.

Check. Throughput before and after each change (dropping one projection: 1,984 → 2,653 docs/s; batch 1k / 5k / 20k over a 1.33 s round trip: 770 / 4,168 / 8,097 docs/s). Failures collected and reported at exit.

Limits. Server-side aggregation moves load to the database; size its disk and check allowDiskUse spill before you rely on it.

12. Gate every setup check on production's code path; size the pod before adding a heavyweight client

When. A configuration passes its setup wizard and fails in production. The first probe using a heavyweight client inside an API pod is OOM-killed.

Do. Build the wizard as a state machine (Source → Access → Extraction → Save, canNext = step === 0 || passed[step], loading a saved config resets both) where every green check is produced by the same functions production runs: the access step replays the exact strategy (lightweight client; heavyweight client to obtain credentials then lightweight replay; or heavyweight throughout), the extraction step replays the production transform on the cached response. Keep the probe classifier dumb:

blocked = status in (403, 429, 503) or (len(body) < 8000 and BLOCK_RX.search(body[:20_000]))
ok      = 200 <= status < 300 and len(body) > 4000 and not blocked

Raise pod limits before the first launch (2 CPU / 2 GiB for a client that adds 400 to 800 MiB) and pin the client, its driver and its fingerprint library together at one protocol revision. Generate any config-write allow-list from the consumer's own enums. Render a model's self-reported confidence as the weakest signal on the screen, marked "not verified"; let measured hit rates decide.

Why. A check that does not execute production's code proves nothing about production. An allow-list that drifts from its consumer silently rejects valid shapes. A heavyweight client is a resource-class change, not a dependency.

Check. Frontend build plus backend import on every change; the probe rule against known blocked and known good responses.

Limits. The classifier thresholds (8,000 / 4,000 bytes) are tuned for document-sized responses; re-derive them for APIs.

D. One generative slot between deterministic gates

Rules 13 to 19 apply when you let a language model propose a replacement query expression (a path predicate over a tree-structured document) whenever an existing expression stops yielding a field. The rule everything else depends on: deterministic code before and after exactly one model call, each stage a subprocess behind a dispatcher, and a single writer (human approval) for live configuration. Nothing the model says reaches production until deterministic code has run it.

13. Triage by aggregation, cluster by structure, send a bounded window

When. You are about to send failed documents to a model and it either answers on nothing or answers on everything, wrongly, while burning its context on index documents, boilerplate and executable payloads.

Do. Triage first, in one aggregation with an exclusive $switch, first rule wins, bodies never decoded: blocked if status ∈ {403, 429, 503, 520}; dead_url if ∈ {404, 410}; infra if status ≥ 500 and no body; fixable if the transform failed with a body and a 2xx or null status; else other. Assert the buckets sum to the total. Expect under half to be fixable.

Then cluster per expression: sample 30 failed documents; fingerprint each as a hard key {block_stub | has_structured_block | size_bucket} (size edges 2k / 20k / 100k / 500k characters) plus the vocabulary of its structural attribute tokens, the labels a template author attached to nodes. Greedy single pass: a document joins the first cluster in its hard-key bucket whose vocabulary has Jaccard similarity ≥ 0.85 with its own and widens the cluster's set to the union; otherwise it opens a cluster. Drop clusters under 5% share. Decide document kind (single entity, index, blocked, not found) with ordered rules, the decisive one being the label of the top-level container, then by counting repeated sibling blocks: index = blocks ≥ 10 ∨ (paginated ∧ blocks ≥ 4) ∨ values ≥ 5. Expect two orders of magnitude fewer documents to reach the model than failures came in.

Then prune each representative into a window with a three-stage function and fixed bounds. Denoise: remove subtrees with no semantics for the task (presentation, comments, vector graphics, executable payloads) except payloads that serialise application state, which in client-rendered documents are the only copy of the value; cap 120k characters. Localise: keep a header window (title, first two structured blocks ≤ 4k each, ≤ 12 metadata entries, ≤ 8k total) and one target window: enumerate anchor candidates in a fixed priority order of attribute patterns (≤ 60 per pattern), keep only those whose text or value attribute matches the field's value shape, reject any whose 8 nearest ancestors include a boilerplate region, grow upward until the window holds ≥ 1,200 characters and continue while the parent stays ≤ 25,000; primary window ≤ 30k, a sibling document's ≤ 18k; under 800 characters send the whole denoised document. Orient: supply the anchor's ancestor path (≤ 6 levels, label plus identifier or first two attribute tokens) as a separate line. Expect the windows to total about a quarter of the denoised size.

Why. Content varies within a template; label vocabulary does not, so structure clusters and content does not. An index document with twenty copies of the target attribute passes any single-match test; only counting catches it. The first value-shaped node in a document is usually boilerplate; anchoring by value shape and ancestor rejection avoids it. A path lets the model express a location structurally instead of guessing.

Check. The triage invariant on every run; cluster counts per expression (most single-mode, a minority with two or three templates); the effect of each pruning rule measured on a frozen benchmark (rule 18).

Limits. The similarity threshold and size buckets are for markup-heavy documents; re-tune for terse formats where the label vocabulary is small.

14. Budget reasoning as its own resource, and decode deterministically when you benchmark

When. With extended reasoning on, most benchmark inputs come back empty with finish_reason = length. Two identical runs at temperature 0.1 disagree on a handful of slots and move your headline number.

Do. Keep the total pool moderate and add a server-side hard stop on the thinking block:

extra_body = {"chat_template_kwargs": {"enable_thinking": True},
              "thinking_token_budget": 512}          # useful range 256–768
temperature = 0.0; seed = <fixed>; max_tokens = 2000
# server: --reasoning-parser ... --reasoning-config {"<think>","</think>"}
raw = choice.message.content or getattr(choice.message, "reasoning_content", "")

Record finish_reason, output tokens, elapsed time and retries per input. If you later swap in a model without a reasoning block, switch the reasoning parser off or its whole answer lands in reasoning_content.

Why. max_tokens is one shared pool; a reasoning model given 6,000 tokens spends them all thinking and answers with none. Sampling makes the evaluation non-reproducible at the granularity you report.

Check. Unbounded thinking at 1,200 and 6,000 tokens left 19 of 23 inputs empty; capped at 512, 11 of 11 fields usable. Greedy decoding with a seed reproduced 43 of 46 slots across versions.

Limits. Determinism is per model build and server version; re-measure it when either changes.

15. Put a mechanical evaluator in the loop, ask once, and reward withdrawal

When. The model answers on every field and the answers fail on the very input they were written against.

Do. Run every proposed expression locally with the consumer's query engine and return the first applicable fault from an ordered list: does not compile → matched nothing → matched N > 1 (state that the consumer takes the first match) → bound to a single instance (an identifier of three or more digits, a positional predicate) → coupled to an attribute that encodes state rather than structure → categorical field returned a unit-only or label-only string → numeric field's string has no digit. If a known-good document is available, add: zero matches on it, or a value different from the reference recorded there (numeric within 0.01, categorical exact). On any fault, append the assistant turn plus one user message that ends "null is a correct answer", ask exactly once, keep the revision only if it parses. If you escalate to a larger model, give it the base answer as an assistant turn plus the faults, no thinking, no second round, and escalate only when the evaluator rejected the final answer or the first model withdrew.

Why. The model cannot execute what it proposes; the evaluator can, in milliseconds. The model's contribution is bounded by the window it sees, so a larger model on the same window repeats the same fault classes.

Check. On a frozen benchmark one feedback round kept the same eight good expressions while junk fell from 12 to 3 and declines rose from 3 to 19. A three-times-larger model on the same windows fixed 22% of bad fields on the easier slice, none on the harder one, and broke working fields. Expect to not adopt it.

Limits. One round. A second round mostly produces variations on the same fault; spend the budget on the window instead.

16. Verdicts in a fixed order, combinators with the consumer's semantics, trials that report two numbers

When. A proposal scores "33 of 33" and is returning a label on every input. A small candidate overwrites three larger repairs for the same field. Rows one producer wrote retire rows another producer needs.

Do. Replay every proposal through the production parser and assign one verdict in fixed order: invalid → no_value → wrong_kind → instance_specific → ambiguous → usable; cross-validate on the expression's other sampled inputs and demote zero cross-hits to instance_specific. Publish in two passes: verify everything, then merge per (expression, field), summing impact for identical candidates and ranking by verdict, then cross-hits, then share. If the consumer supports chains for a field, check the chain with the consumer's own semantics (first candidate in order whose text parses wins, not a union), and mark it usable only if it hits on every sampled input and every member is usable; do not chain fields where the same syntax means union. Key stored proposals by every dimension that can legitimately differ, (expression, field, source). Trial current against proposed on 50 failed inputs of the right kind and 50 known-good inputs; a hit is a non-empty right-kind value; report losses (current hit, proposed miss, failed set) and regressions (same, known-good set) separately, and derive the verdict unverifiable → regression → gain → loss → no_gain. Show a distribution of returned values so "33 identical label strings" is visible.

Why. Presence counts cannot tell a value from a label. An upsert keyed too coarsely keeps whichever run came last. Two measurements under one label hide the important half.

Check. A previously overwritten case should show the merged chain hitting on all sampled inputs and its trial move from 0/50 to 50/50 after the key change.

Limits. Trials on 50 + 50 inputs bound the regression you can see; size them by rule 17.

17. Validate against inputs that still work, sized by the regression rate you must catch

When. Proposals pass every check (unique match, plausible value, no positional anchors) and still break the field on most inputs once published.

Do. Add a success gate at publish time and inside the loop over a sample of known-good inputs that carry the value production extracted from that exact body:

got = evaluate(doc.body, final_expression, field).get("value")
if not got:                      lost += 1
elif abs(float(got) - float(doc.reference)) > 0.01: mismatch += 1
if (lost + mismatch) and verdict in ("usable", "ambiguous"):
    verdict = "regressive"       # store counts and up to 3 mismatch samples on the row

Size the sample from the escape probability: a proposal that breaks a fraction p of known-good inputs escapes a gate of n with probability (1−p)n; for p = 5%, n = 25 gives 0.28 and n = 50 gives 0.08. Before proposing, run the current expression over the sampled failed inputs and mark the proposal current_works when it yields on all of them (the failure is elsewhere). Treat a human rejection as a terminal state in the upsert filter: suppress an identical re-proposal, re-file a different one with the rejection history attached. Surface the null outcome: an expression whose failed inputs are all of the wrong kind produces one policy row, asked once (status $nin [approved, rejected]), not thousands of "failures" per run. Before adding a dependency to close a suspected gap, measure the gap (a parser-drift script found 3.2% of decisions depended on the parser and 28% were misses under both; the dependency was not added).

Why. A validation set drawn only from failures cannot show a regression: a proposal for a minority template that matches nothing on the majority layout, or one that picks a neighbouring node with a plausible but different value, is invisible there.

Check. Synthetic inputs: minority-template and wrong-node proposals draw faults, correct ones stay silent, an empty corpus is silent. A decision table for rejections: same candidate suppressed, different candidate re-filed with history, approved untouched, pending refreshed.

Limits. The gate needs reference values on the known-good inputs; without them you can only measure "lost", not "wrong".

18. Benchmark by re-scoring frozen inputs, and rank by cost per usable output

When. Two runs a week apart cannot be compared: the evaluator changed, the inputs changed, the temperature was non-zero.

Do. Write the ground rules down and enforce them in tooling: re-score rather than re-read (a report command recomputes every historical verdict with today's evaluator); same frozen input set, temperature 0, fixed seed; the production parser is the oracle; inputs of the wrong kind leave accuracy denominators; unparseable output counts under stability, not accuracy. Define metrics as formulas: precision = usable / proposed (declines excluded); yield = usable / (inputs × fields); decline and wrong-decline rate; hold-on-siblings = cross_hits / cross_inputs; gain and loss on failed inputs; regression on known-good inputs as a gate that must be zero; agreement with a reference (numeric within 0.01 at the gate, 0.005 in the master comparison); parser drift; latency as median and tail per input, output tokens, runaway rate (hit the cap unfinished), feedback-round frequency; determinism as identical answers on rerun; confidence calibration. Report per-source distributions, never a mean. Rank configurations by cost per usable output, tie broken by precision. Version the evaluation set per cycle, store it rather than re-fetch, and include per scenario a stated trap, a negative input where null is correct, at least two layouts and one known-good input per source.

Why. A benchmark whose oracle moves measures the oracle. A mean over sources hides that one source carries the number.

Check. A series on 23 frozen inputs should be reproducible step by step: generic prompt 3/4 usable but answering almost nothing; repair framing 6/15; focused window plus sibling 8/20; two more prompt rules 8/14; one feedback round 8/11; unbounded thinking 0/0; capped thinking 11/11; temperature 0 plus seed 10/11. In production, expect the known-good lane to settle in the high seventies percent and the failed-input lane around half, and most non-usable proposals to be dropped automatically before review (of 442, 301 were).

Limits. Frozen inputs age; refresh the set per cycle from new failure modes, but keep old versions to compare against.

19. When porting regular expressions, port the flags' semantics, not the syntax

When. Legacy patterns moved from PHP preg_* to Python re fail to compile or capture the whole document.

Do. Parse delimiter and flags; map s/i/m/x; honour PCRE U by rewriting the greediness of every quantifier outside escapes and character classes (+ ↔ +?, counted {m,n} likewise). Strip nested markup and collapse whitespace from the capture before numeric cleaning. Order the strategy after structured data and the primary expression, and give it the same preference flag as the primary one so a source configured only with patterns is not shipped empty.

Why. U inverts greediness globally and has no Python equivalent; @open(.+)close@Us becomes a greedy capture to the last closing delimiter.

Check. Every pattern compiles; a live re-validation should move the large majority of former "invalid" results to "ok", leaving a handful of genuine no-matches.

Limits. Other PCRE-only constructs (possessive quantifiers, some verbs) need their own translation; audit every branch written before the new strategy existed.

E. Sticky sessions and upstream identity

20. Substitute placeholders after every encoding step, and enforce identifier invariants at write and read

When. Hundreds of independent client sessions leave a gateway through one upstream address; sessions for different regions share an address; "move on flag" does nothing. Or every request through a gateway fails with "Unsupported proxy syntax".

Do. Recognise the placeholder raw and percent-encoded ({session} and %7Bsession%7D), case-insensitively, at every step it passes through, and resolve it per namespace (host#stream) so every piece of per-session state is keyed together. Use two patterns for identifiers, one to mint and one to validate, or a single pattern will flag every minted token and re-mint per request, destroying stickiness:

_SLUG_UNSAFE  = re.compile(r"[^a-z0-9]+")   # minting: collapse to a slug
_TOKEN_UNSAFE = re.compile(r"[^a-z0-9-]")   # validation: re-mint stored tokens in place

Treat an access token as bound to source address and client fingerprint: drop the token store when the pinned fingerprint is missing or when two fingerprint dimensions contradict each other (declared client family versus transport-layer family). When merging token lists from incremental renewals, dedupe by name keeping the latest expires.

Why. A placeholder that is never substituted is not a no-op; the upstream treats the literal as one session id for everyone. A # in a credential URL is a fragment delimiter. A fingerprint contradiction is a positive signal of automation, not a degraded request. Assignment-order merging keeps the older token, bound to an address that has since rotated away.

Check. Measure on the gateway: the literal placeholder should resolve to one address and a per-host token to a different one. Unit-test every failure path of any new session mode falling back to a fresh session.

Limits. Two-pattern minting only works if stored tokens can be re-minted in place on read; otherwise invalid stored tokens fail until they expire.

21. Make rotation policy per upstream; know that reassignment is bounded by pool size

When. A "move the session to a fresh address" operation ping-pongs between two already-flagged addresses.

Do. Offer three reactions to a flagged address and choose per upstream, with a comment recording why it was last changed: mint a new session; rotate (reconnect the bound tunnel: a genuinely new address on the same pod, slow, disturbs other sessions there); reassign (move to another already-connected pod in the same region: fast, token unchanged). Make every new mode fall back to a fresh session on any failure path (no base URL, 404, non-200, unreachable, no live token). For upstreams that limit per address, run a pinned pool: admit an address in three steps (echo it un-pinned, rebuild the credential with the pin and echo again requiring the same address, fetch requiring the configured status and no challenge markers); keep leases in a sorted set scored by available_at; evict only on the configured flag statuses, never on resource-level errors like 404; draw any rotate-every-N threshold once per cycle.

Why. Reassignment cycles among existing pods, so on a two-pod pool its reachable set has size two; freshness on a small pool needs reconnection. Re-rolling a random threshold per request makes the effective threshold the minimum of N draws.

Check. Render every configuration and diff against the previous render so exactly the intended upstreams change. Unit-test the fallbacks.

Limits. The pinned pool assumes the upstream keys its limits on address; where it keys on the token, the pool multiplies cost for nothing.

22. Count the identities isolation forces you to keep alive before you split a stream

When. Splitting one queue into N isolated streams on the same region makes throughput worse.

Do. Before splitting, count what each stream must own: its own token store, access token, session token, fingerprint pool and breaker, hence its own acquisition per renewal cycle. Compare N acquisitions per cycle against the acquisition step's throughput when that step runs one process-wide. Check whether streams on one region actually get distinct addresses (six tokens on one region landed on two). If the split is only for failure isolation and independent sizing, say so and size accordingly; if it was for address diversity, it does not deliver it. Keep the stream count in the queue registry so setup derives shards from one source. When you revert, leave the configuration commented in place with the reason next to it.

Why. The binding constraint on isolation is the number of identities the acquisition path can sustain, not pod count. Streams on the same region still share one address's rate budget.

Check. Render configs and diff against the previous render; check deployment names against registered shards one-for-one.

Limits. If the acquisition step scales horizontally, the constraint moves; re-measure it rather than reusing this rule.

If you keep one rule: a container restart reuses the network namespace, the sandbox's resolv.conf and every pod-scoped volume. Four of the twenty-three rules (duplicate firewall and routing entries, the emptied resolv.conf, the logout-on-restart storm, the ghost lease holders) are the same mistake, a start-up script written as if it runs once. Make every mutation at start idempotent, and every cleanup conditional on deletionTimestamp.

F. Geometry

23. Drive a rigged skeleton from joint positions by stretching bones, not by inverse kinematics

When. You have per-frame joint positions and a skinned character whose bones want rotations; wrists drift, and one joint lands exactly while the next one down the chain lands far off.

Do. Per bone, top-down: inherit the parent's rotation change since rest; swing the rest direction onto the data segment with setFromUnitVectors; take roll from an explicit hint (hip line, shoulder line, bend plane), blended to the inherited roll when the hint's perpendicular component falls below 0.12 of unit length; re-length limb bones to the data segment each frame, reading the segment head from where the bone actually is; drop any cached transform for a bone the moment its rotation is solved. Push baked animations through the same solver instead of copying quaternion tracks between rigs.

Why. Rotation alone cannot correct bone length, so error accumulates down each chain. A world matrix cached when a bone's position is read, before its rotation is solved, leaves the child composing against a stale parent. Quaternion tracks do not transfer between rigs whose bone frames differ.

Check. Headless, over every frame in your data and every rig: limb joint error 0.0, roll error 0 wherever the hint is strong, every clip poses a standing body. Details in the retargeting post.

Limits. Stretching is invisible at a few percent; if the model's proportions differ grossly from the data, use IK for the end effectors instead.

Open claims, stated so they can be wrong

  • A linter that flags iptables -I, ip rule add and echo >> /etc/resolv.conf without a preceding delete loop would catch four of these twenty-three rules at review time.
  • The half-open interval rule (8) applies to every "process since watermark" loop over a mutable field, including log tailers keyed on modification time. A counterexample would be a scan where writers only ever decrease the key.
  • With a deterministic evaluator in the loop, a model's repair rate is bounded by the window it is shown, not by its size (15). Falsified if a larger model on an unchanged window fixes the "matched several nodes" fault class, which is the largest one.
  • The escape probability (1−p)n (17) is the right sizing rule for any publish gate, and the right n makes the escape probability lower than the human review rate. The 50 above was chosen to match the failed sample, not derived.
