Notebook, August: what 223 commits taught me

I pointed a script at a month of git history across ten repos, kept only my own commits, flagged every revert and second fix, and wrote down what those commits knew that the ones before them did not. Names of shops, vendors and colleagues are scrubbed; the techniques are the point.

I Ierofantis · 9 min read · monthly notebook, from git history
📓

A changelog tells you what shipped. A notebook tells you what you would do differently, and that lives in a different set of commits: the revert, the fix that follows a fix, the config flipped on Tuesday and flipped back on Thursday. So the script that produced this post does one thing a git log does not: it flags any commit whose message smells like a lesson (fix, revert, instead, was blocking, back to) and hands me those first. August had 223 commits of mine across eight active repos, most of them in a crawler platform I work on, the rest in an egress fleet, a blog and four small games. Below are the seven lessons the flagged commits agreed on.

One rule before the list. The work repos serve real clients against real retail sites, so every retailer is "Shop A" or "a price-comparison site", every network vendor is "Provider B", teammates are "a teammate", and there are no volumes, replica counts or market names. The redaction runs in the script, before the commit messages ever reach a draft, which is the only place it can be trusted to run.

1. When the gateway is unreachable, suspect the routing before the fail-closed rule

The egress fleet runs tunnel clients in pods behind a gateway. A new upstream vendor joined this month and its pods came up green while the gateway could not reach them. The first theory, everyone's first theory, was the client's fail-closed rule dropping traffic. Three fixes later the commit message that stuck read "asymmetric routing, not the fail-closed DROP": replies were leaving through the tunnel while requests had arrived on the pod network, so the gateway saw a black hole that looked exactly like a firewall.

The same week produced the rest of the checklist for wrapping any tunnel client in a container: point the local proxy daemon's DNS at the tunnel's own resolver instead of the cluster's; disable the client's fail-closed mode before the first connect; verify that "enable in background" and "connect" actually succeeded rather than trusting their exit codes; and, the one that bit twice this month across two vendors, iptables rules accumulate when a pod restarts in place, so a script that adds rules must also delete them. A restart in place is not a fresh pod. Assume the previous life left furniture behind.

2. A self-healing selector has to prove itself where things still work

The crawler has a healer: when a site changes its markup and a CSS selector stops extracting a field, the healer proposes a replacement mined from the pages that failed. In July the healer validated proposals against the failed pages only. Obvious, and wrong. A selector that matches the new layout can still break the old one, and most of the fleet was still on the old one.

Four commits in one week turned that around: validate every proposal against a sample of working pages as well as the failed set, at publish time and again inside the healing loop; demote a proposal when the field it "fixes" already extracts fine on those pages; remember rejections so a proposal a human turned down is never silently re-filed; and route the genuinely unfixable ones into a single policy card instead of an eternal, silent retry. The rule generalises to any automated repair: the test set must include the cases that currently pass, or the repair will optimise for the failure and quietly burn the rest.

3. Keep the revert in place

Queue topology was the month's flip-flop. One shop was split into lanes, one country per lane, then given more lanes, then put back on one queue, then split again with a different worker count, all within two days as the site's behaviour changed under us. Two habits made the flip-flopping cheap instead of chaotic. The first: when a feature is disabled, leave its configuration commented in place rather than deleted, so the next enable is an uncomment and a diff, not an archaeology dig. The second, straight from a commit subject: "document the revert in place", meaning the reason it was turned off lives next to the switch.

The largest commit of the month was also a revert, of a whole pull request, hundreds of files. It was the right call. Partially reverting a big change leaves you with a state nobody has ever tested. Revert the unit that was reviewed, then re-land the parts that were fine.

The month's reframe: every revert was a lesson the forward commit did not have yet. Reading the flagged commits in pairs, the change and its undo, teaches more than reading either alone, because the pair contains the theory that turned out to be wrong.

4. splitlines() is not split("\n")

A diagnosis tool uploaded JSONL from a reused pod and some records arrived corrupted. The culprit was Python's str.splitlines(), which splits on every Unicode line boundary, including characters like U+2028 that had been sitting harmlessly inside JSON string values. One record became two half-records. split("\n") is the correct tool for a line-delimited format, precisely because it is dumber. The same repo taught two neighbours of this lesson: store failed page bodies in their own collection rather than in the state document that everything else reads, and when a cache is rebuilt from scratch, write it with $out (replace) instead of $merge, so a full rebuild cannot inherit stale rows from the previous build. Hot state small, blobs elsewhere, rebuilds that replace.

5. Rotation policy belongs to the target, not the platform

An earlier post argued that an exit address is part of a scraper's identity. This month tested how far that goes. For one site, a pinned pool of exit addresses per session worked; for another, the same pool got the whole pool burned faster, and the config went back to plain rotation within the day. Then a middle mode appeared: reassign, where a session that gets flagged is moved to a new exit and stays there, as opposed to rotating on every request. Selectors that need a clearance cookie re-warmed were flipped to reassign, then some were flipped back.

The lesson has nothing to do with which mode is right. There is no platform-wide answer, so the mode has to be a per-target setting with a cheap switch, and the anti-scan state that goes with it (clearance cookies bound to an address and a user agent) has to be isolated per lane or a change on one target poisons another. One fix this month was exactly that: a clearance cookie's binding to IP and UA had drifted, and the tokens used to pin a session to an exit were not URL-safe, so pinning silently failed on some paths. Identity has to be coherent end to end, or it is theatre.

6. Deployment config is code, and it has bugs

The dumbest failures of the month were all in files nobody unit-tests. A game's Render build failed because NODE_ENV=production makes npm install skip dev dependencies, and the bundler was one; the fix is npm install --include=dev in the build command. A hosted service kept flipping back to the sleeping free tier every time the blueprint synced, until the plan was pinned in the blueprint itself. A Helm upgrade hung on a new major version's watcher, fixed with --wait=legacy. A CI server's concurrency control turned out to be broken, and a teammate replaced it with a self-implemented deploy lock. The gateway's health checks were flapping until they got hysteresis, and rotations got a circuit breaker so a failing pod could not be rotated into forever.

None of these is a systems insight. All of them cost hours. The habit I am taking into September: every deploy-side fix gets a one-line comment at the place it lives saying which failure it prevents, because the next person to "clean up" that flag will be me.

7. Prove the geometry in numbers before you look at it

On the games side the month was retargeting GrappleMap's joint positions onto rigged 3D avatars, and the thing that made it possible was having no browser while writing it. The solver had to pass a headless test over every position in the database before I saw a single frame, and the two real bugs (a stale matrix cache, a model exported facing the wrong way) were caught by the test in one line each. Measurement first, pixels last; the same instinct as lesson 2, from the other side of the screen.

How the notebook gets made

The script is small: for each repo, git log --numstat since a date, own commits only, grouped by week, with a redaction map applied to subjects, bodies and paths before anything is written, and private repos reduced to top-level directories. It flags lesson-shaped commits and prints them first. Then the writing is manual, on purpose: the script finds where the learning is, it does not know what the learning was. The redaction map is the one file that holds real names, and it never leaves the machine.

Open question for September: two of the seven lessons are about the boundary between "a fresh start" and "a restart in place", pods and caches both. I suspect there is one principle under them, and I do not have it yet.
