Find your own origin before someone else does

A CDN protects your server by hiding its address. If that address has leaked, every rate limit and filter it enforces can be walked around. Here is the audit, run against yourself.

I Ierofantis · 8 min read · adapted from The Quiet Fetch
🕵️
This is a defensive piece. Every technique here is meant to be run against infrastructure you own, or under a written engagement. Pointed at anything else, it is trespass. The reason to know it is that an attacker knows it, and you cannot fix an exposure you have not looked for.

A defense in front of a website works by standing between the internet and the real server, so all traffic passes through the defense and none reaches the server directly. The whole model depends on one secret: the origin's address. If a request can reach the origin directly, it bypasses every protection the CDN provides, its rate limits, its filtering, its challenge, all of it. So the single most useful audit you can run is: can I find my own origin?

The whole chapter in one line: the list of ways an origin leaks is, read backwards, your hardening checklist. Each leak has a specific remedy.

The leaks

An origin escapes into public data in a handful of predictable ways.

  • Unfronted subdomains. Sites proxy www and api through the CDN and forget mail, dev, staging, vpn. Certificate transparency logs list every hostname ever certified, whether or not it is linked anywhere. Many resolve straight to the origin's network.
  • Mail. A web CDN cannot front SMTP, so the MX records point at real infrastructure, often in the same range as the web origin. The SPF record sometimes hardcodes the origin's egress range outright.
  • History. A site that adopted its CDN later had a public address before that. If the origin still lives there, historical DNS hands it over.
  • Reused certificates. Many origins serve the same TLS certificate the CDN does. Internet-wide scanners index every server's cert; ask which addresses present yours, filter out the CDN, and the rest are candidates.
  • Favicon and other fingerprints. The same icon served from origin, staging, and dev hashes identically, and scanners index that hash across the whole internet.

Confirming a candidate

Given a suspect address, confirmation is direct: talk to that address while presenting the real hostname, as if the CDN were not there, and see whether it answers with the site's real content. On the command line that is one flag:

curl -k --resolve example.com:443:<candidate-ip> https://example.com/ -s -o /dev/null -w "%{http_code} %{size_download}\n"
# 200 88214   → real content, direct to origin. Exposed.
# 000 0       → connection dropped at the firewall. Properly hidden.

A real body means the origin is reachable around the defense. That is the finding.

Closing the leaks

Now read the list backwards. Put the auxiliary hosts and mail behind the CDN or firewall them. Lock the origin to accept connections only from the CDN's IP ranges. Retire the historical address. Serve a distinct certificate at the origin so the cert scan misses. Strip the literal range from the SPF record. When every leak is closed, the origin makes only outbound connections or refuses anything that is not the CDN, and the whole audit above comes back empty. That empty result is the goal state, and the only way to earn confidence in it is to have looked.
